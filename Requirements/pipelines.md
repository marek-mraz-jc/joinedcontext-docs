# Pipeline Execution & Processing

Family **PL** (PL-01…PL-114). Owning chapter: [Architecture/08-pipelines.md](../Architecture/08-pipelines.md). Verified by: [Testing/04-configuration-and-pipeline-tests.md](../Testing/04-configuration-and-pipeline-tests.md).

## 1. Manifest Envelope and Native Payloads

- **PL-01** [P] — A Pipeline MUST be declared within an organization repository as a folder `projects/{project}/pipelines/{name}/` containing a `pipeline.yaml` platform envelope and a native `bento.yaml` definition.
- **PL-02** [P] — The platform envelope `pipeline.yaml` MUST adhere to JSON Schema draft-07 and declare `metadata.name`, `spec.class`, `spec.targetEndpoint`, `spec.secretRefs`, and `spec.quotas`.
- **PL-03** [P] — The pipeline definition `bento.yaml` MUST remain valid native Bento configuration without proprietary DSL wrapping or custom AST parsing (CC-11).
- **PL-39** [P] — A Pipeline MAY declare `spec.source.dataSourceRef`, and the reconciler MUST then render the referenced connection as the native Bento input of the generated `bento.yaml` and leave the author's processors and output untouched (MF-35, PL-03).
  > Note: A reference resolves inside the pipeline's own project, excludes `endpointRef` and an author-written `input`, and fails the plan when it names no existing `DataSource`; see [Architecture/08-pipelines.md §6](../Architecture/08-pipelines.md#6-external-feeds-the-datasource-kind-mf-35-pl-39).

## 2. Execution Classes and Scheduling Rules

- **PL-04** [P] — The platform MUST support two execution modes: resident streams mode within a project-dedicated Pipeline Runner Deployment, and scheduled mode via ephemeral Kubernetes CronJobs.
- **PL-05** [P] — When `spec.class` is set to `auto`, the reconciler MUST assign streaming inputs or polling cadences under 30 seconds to resident mode, and cadences of 30 seconds or longer to scheduled mode.
- **PL-06** [P] — Synchronous request/response HTTP services MUST NOT be hosted as pipelines, delegating client-facing APIs exclusively to the Context Gateway (EP-05).

## 3. Process and Runner Isolation

- **PL-07** [S] — Pipelines belonging to different Projects MUST NOT share runtime processes, heaps, or operating system containers.
- **PL-08** [P] — Every Project containing active resident pipelines MUST be provisioned with a dedicated Pipeline Runner Deployment running Bento in streams mode.
- **PL-09** [P] — Adding, updating, or deleting a resident stream within a Project MUST update the streams ConfigMap and trigger dynamic stream reloading without restarting the runner pod.
- **PL-10** [S] — Scheduled pipelines MUST execute in isolated Kubernetes Pods created by CronJobs, running under non-root service accounts scoped strictly to the owning Project.

## 4. Quotas, Resource Limits, and Memory Budgets

- **PL-11** [P] — The default resource allocation for a project Pipeline Runner Deployment SHALL be memory request `256Mi`, limit `1024Mi`, and CPU request `100m`, limit `1000m`.
- **PL-12** [P] — An individual Pipeline Runner Deployment MUST NOT host more than 50 concurrent resident streams, partitioning across multiple runner pools when exceeded.
- **PL-13** [P] — Idle resident streams MUST maintain a memory footprint not exceeding 30 MiB per stream.
  > Note: Not measured yet. [Architecture/08 §2](../Architecture/08-pipelines.md#2-bento-streams-mode-architecture) gives 15–30 MiB as the range observed, and no benchmark holds a runner to it. The check is a runner benchmark in the performance lane ([Testing/05 §5](../Testing/05-deployment-and-performance-tests.md#5-the-k6-budgets)): idle streams added one by one, the runner's resident memory read after each. Phase `next`.

## 5. Secret Handling and Reference Resolution

- **PL-14** [S] — Secret credentials MUST NOT be authored in `bento.yaml` or `pipeline.yaml` in plaintext (CC-06).
- **PL-15** [S] — Secret references declared in `spec.secretRefs` MUST be resolved by the reconciler from the platform secret store at apply time and injected as environment variables or mounted files.
- **PL-16** [S] — In `bento.yaml`, secret values MUST be referenced strictly using Bento environment variable interpolation syntax.
- **PL-17** [S] — Runner pod logs, status events, and reconciler outputs MUST redact all injected secret values.

## 6. Service Identities and Write Gateway Flow

- **PL-18** [S] — A pipeline writing data into an internal Context Space MUST communicate exclusively with the Context Gateway or internal broker listener; direct manipulation of the underlying database is strictly prohibited.
- **PL-19** [S] — Every Pipeline MUST run as its own principal: a ServiceAccount `pl-{pipeline}` derived from the Pipeline (the prefix `pl-` is reserved, and a ServiceAccount manifest of that name MUST be refused), bound to its own Kubernetes ServiceAccount `pl-{project}-{pipeline}` in `{instance}-pipeline-identities`, a namespace that holds the pipelines' ServiceAccounts alone, whose Keycloak client `{project}-pl-{pipeline}` authenticates with federated client authentication (PF-47) and holds no secret. The runner MUST obtain each token through the token service beside it, the one pod of its namespace that reaches the Kubernetes API, which may mint a token in that namespace and nowhere else and mints one for that one ServiceAccount (TokenRequest, audience the realm issuer, at most 600 s) per request and presents it as the client assertion; a stream MUST name only its own pipeline. The Portal's reconciler MUST keep one such Kubernetes ServiceAccount per Pipeline in the namespace `JC_PORTAL_PIPELINE_NAMESPACE` names, and delete it with its Pipeline. Until the deployment switches it on (`JC_PORTAL_PIPELINE_IDENTITY=pipeline`, which the Portal refuses without that namespace), streams keep the project's `pipelines` account (owner decision 2026-10-06, T-1508, option a2; Architecture/12 §3). The pipeline-test harness and the DataSource probes (PL-43, MF-39) run as `{project}/pipeline-test` the same way, a principal with the Portal's internal audience alone; the Pipeline name `pipeline-test` is reserved and MUST be refused (T-4050).
- **PL-20** [S] — For every Pipeline the reconciler MUST derive the Policies of its principal `pl-{pipeline}` and no wider: on the space of each output's Endpoint, `upsertBatch`, `createBatch` and `queryBatch` over the output's `type`, which is the URN prefix `urn:ngsi-ld:{type}:{orgDomain}:{space}:` the pipeline writes (PF-42), plus `deleteBatch` when `spec.expiry` is set (PL-64); on the space of an Endpoint source, `retrieveOps` over the source query's `type`. A Policy written by hand MUST NOT name a `pl-` principal (CC-61, T-1509).
- **PL-94** [S] — A Pipeline MUST reach only what the people who propose and approve it reach (T-4893): every door that writes a Pipeline (the resource route and the operations and assistant tools behind it, an import, a blueprint, a workspace brought back, and each approval) MUST refuse it `403` unless the caller holds, in the Pipeline's project, `read` on each `DataSource` a source names (that manifest, under the role's constraints; an MQTT DataSource's broker and topics are read through it), `read` on `Entity` in the space of each source Endpoint whose audience is not `public` (the right DM-74 and Explore read entities with), and on the space of each output's Endpoint both the door's own verb on `Pipeline` (`propose`, or `approve` at approval; a project grant or one bound to that space, T-4593) and `read` on `Entity`. The refusal reads `No access to {reference}` for each reference as the manifest writes it (`DataSource feed`, `source Endpoint ep-b`, `target Endpoint ep-a`) and MUST NOT name the space behind an Endpoint or count anything the caller cannot read; the bootstrap group passes, and deleting a Pipeline asks only `delete`. The editor's source and target pickers list only what these rules let the person use. Decided (worker-t4893, owner may override): write on a target is the Pipeline verb in the target's space, not a data-write verb on `Entity`, because no seeded role grants `Entity` beyond `read` and pipeline writes are already bounded by the pipeline account's Policies (PL-20).
- **PL-95** [S] — The reconciler MUST re-check PL-94 for the Pipeline's last proposer and approver at each render, read from the merge that brought the manifest in, and a right one of them lost MUST pause the pipeline (`spec.enabled` stays, the stream is left out) with the status reason `author lost access to {reference}` until a person who holds the rights proposes it again; the pipeline account's own grants are PL-90…PL-93's.

## 7. Quality Gates, Egress Control, and Observability

- **PL-21** [P] — CI pipelines MUST execute `bento lint` on every `bento.yaml` file prior to merging.
- **PL-22** [P] — CI pipelines MUST execute automated golden input/output tests for transformation pipelines (`bento test ./...`) asserting expected output structures.
  > Note: The platform's own lane runs both over the recipes it ships (`joinedcontext-platform/.github/workflows/ci.yml`: `bento lint ./examples/ingestion/*/bento.yaml`, `bento test ./examples/ingestion/...`). A project's own `bento.yaml` never passes through that lane; the runner lints it, and the pipeline test returns those lint errors with their line numbers before the pipeline is proposed (PL-43).
- **PL-23** [S] — NetworkPolicies applied to Pipeline Runner pods MUST enforce default-deny egress, permitting connections only to the Context Gateway port, explicitly declared external targets, and in-cluster DNS.
- **PL-24** [P] — Resident Pipeline Runners MUST expose Prometheus metrics on a dedicated port (`/metrics`), exporting per-stream throughput, error counts, latency histograms, and buffer depths.
- **PL-25** [P] — Unrecoverable processing failures MUST be routed to an explicit dead-letter mechanism, transitioning consecutive failures exceeding thresholds to `Error` status (CC-33).
  > Note: Not built. Today a write the gateway answers with 400, 413 or 422 drops its batch and counts it under the output's label (the Portal's `reconciler/streams.rs` `gateway_output`), and a stream the runner refuses sets the Pipeline to `Error` with the runner's reason. No dead-letter store and no failure threshold exist. Phase `next`.

## 8. Class Selection Rules

- **PL-26** [P] — With `class: auto`, the reconciler MUST select `resident` when the pipeline trigger period is shorter than 30 seconds or push-based, and `scheduled` when the period is 30 seconds or longer.
- **PL-27** [P] — For `scheduled` pipelines with 30 s ≤ period < 60 s, the reconciler MUST render a CronJob with schedule `* * * * *`, setting `input.generate.interval` to the period and `input.generate.count` to `floor(60 / period)`.
- **PL-28** [P] — An explicit `class: resident` or `class: scheduled` setting MUST override automatic classification, recording the effective class, schedule, and execution settings in `status`.
- **PL-40** [P] — A Pipeline MAY declare `spec.enabled` (default `true`); when it is `false` the reconciler MUST leave a resident stream out of the runner's ConfigMap, MUST render a scheduled pipeline's CronJob with `suspend: true`, and `status` MUST report the pipeline as paused (PL-28, CC-35).

## 9. Mappings with LinkML-Map

- **PL-29** [P] — A Pipeline MAY reference one or more `kind: Mapping` resources through `spec.mappingRef`, injecting compiled Bloblang processors in declared order and failing apply if compiled artifacts are missing or stale (DM-35).
- **PL-30** [P] — Pipelines whose output targets a published Data Model type SHOULD produce that type through a Mapping rather than hand-written Bloblang; CI MUST emit a warning on unmapped entity construction when a published Mapping exists.
  > Note: The warning is not built. Nothing today notices that a hand-written Bloblang produces a type a published Mapping already covers.

## 10. Derived pipelines and compute steps

- **PL-31** — A Pipeline MAY declare `spec.source` with an `endpointRef` (read grant) and either `query` (scheduled: current or temporal query) or `trigger.subscription` (resident: NGSI-LD subscription delivered by the gateway to the runner); the reconciler MUST render the matching Bento input. A `query` read MUST cover every page of the answer (NGSI-LD `count=true` for the total, then `offset` in pages of 1000) and hand the compute one list; an answer holding more than 50,000 entities, or a full first page whose total the endpoint does not state, MUST fail the read rather than pass a cut list on (T-3132).
- **PL-32** — Derived output MUST be written through `spec.targetEndpoint` like any other pipeline (PL-18…PL-20); the target MAY be the same Context Space (new entities, or `output.mode: update-attrs` on the source entities) or another space, including one of another project or organization, if that owner's Endpoint grants the pipeline's ServiceAccount the write operations.
- **PL-33** — `spec.compute.kind` MUST be one of `bloblang`, `mapping`, `wasm`, `container`; CI MUST warn when a heavier kind is used for logic expressible in a lighter one.
  > Note: The four kinds are enforced by the typed parse (`crates/jc-core/src/kinds/pipeline.rs`). The weight warning is not built.
- **PL-41** — A `bloblang` compute step MAY carry its mapping inline as `spec.compute.bloblang`; the reconciler MUST then render it as the last `mapping` processor of the generated `bento.yaml`, after the DataSource input and the source processors, and MUST refuse the field on any other compute kind (PL-33, PL-03).
- **PL-42** — `spec.source.query` MAY carry `ids`, a list of entity URNs the pipeline reads instead of the whole type; each id MUST follow PF-42 with `{Type}` equal to `query.type` when both are set, and the reconciler MUST render them as the `id=` parameter of the fetch, the endpoint's Policy still narrowing the result (PL-31, GW15).
- **PL-34** [S] — `wasm` modules MUST be built in CI from source beside the pipeline (`compute/`) for `wasm32-wasip1`, tested with `cargo test` and `bento test`, stored in the artifact store and pinned by digest in the rendered config; a module MUST NOT have network, filesystem or environment access and MUST run under a per-invocation memory limit.
- **PL-34a** [S] — The digest the reconciler pins MUST be the `joinedcontext.com/module` annotation on the Pipeline manifest, written back by the build lane in the commit that publishes the module to the artifact store; a `wasm` compute without it MUST render no processor and no runtime (PL-34).
- **PL-35** [S] — `container` compute MUST be `scheduled` only, MUST use an image built in CI, signed and pinned by digest, and MUST reach data only through the source and target Endpoints with the pipeline's ServiceAccount token under the runner NetworkPolicy (PL-23).
- **PL-36** — Every derived entity or attribute MUST carry `derivedFrom` (Property: the URNs of the source entities, or of the Endpoint they were read through) and `computedBy` (Property: pipeline URN and module or image digest).
- **PL-37** [S] — The reconciler MUST reject a resident derived pipeline whose output type or attributes intersect its own subscription trigger unless `spec.allowFeedback: true` is set; such a change MUST be at least yellow lane.
- **PL-38** [P] — Derived pipelines MUST ship golden tests: the same source page or notification set MUST yield the same output entities; CI MUST run them (PL-22).
- **PL-45** [H][A] — The Portal MUST offer a `kpi` preset for a derived pipeline (Architecture/08 §3, KPI pipelines): `class: scheduled`, `spec.source.endpointRef` plus `query` over one entity type, a compute of any PL-33 kind that aggregates the page into one `KeyPerformanceIndicator` entity per run with the id `urn:ngsi-ld:KeyPerformanceIndicator:{orgDomain}:{kpiSpace}:{name}` (PF-54) and the attributes of Architecture/03 §2 (`name`, `calculationFormula`, `currentValue` with `unitCode` and `observedAt`, `calculationPeriod`, `updatedAt`, `derivedFrom`, `computedBy`), written through an Endpoint of the indicator space it names, `{project}-kpi` or another space ending with `-kpi` (PF-54), and run on a `schedule` or on every change of the source (`spec.source.trigger.subscription`, PL-51); the preset's `compute.bloblang` MUST pass the test (PL-43) on a page of the source endpoint before it is proposed (PL-49), and an indicator without `calculationFormula`, `derivedFrom` or `computedBy` is refused at admission (PF-43, PL-36), never repaired by the runner.
- **PL-46** [S][A] — A `container` compute step (PL-35) MUST run one CronJob per schedule from an image of the platform's `analysis-runner` family (`python` 3.12 with pandas, `node` 22, or `rust` for a binary built in CI), pinned by digest, selected by `spec.compute.runtime` (`python`, `node`, `rust`), with the script named by `spec.compute.script` and committed beside the pipeline (`compute/main.py`, `compute/main.js`, or `compute/src/main.rs` built in CI); the runner MUST hand the source page to the script as NGSI-LD JSON on stdin and MUST write to the target endpoint exactly the entities the script prints on stdout as one JSON array; a non-zero exit MUST fail the run with the script's stderr as the run's error and write nothing; the wall clock MUST be 60 s (`activeDeadlineSeconds`); the Job's network MUST reach only the gateway (PL-23) and its environment MUST carry nothing beyond `JC_ORG_DOMAIN`, the source and target endpoint URLs and the pipeline's own ServiceAccount token (PL-14).

## 11. Testing a pipeline before proposing it

- **PL-43** [H][A][S] — The Portal MUST answer `POST /api/v1/projects/{project}/pipelines/test` with a stage-by-stage trace of a candidate pipeline run once over a sample (API/01 §7a): the request carries the Pipeline manifest (or its `spec`) and a sample as text (at most 5 MiB, held in memory) or as a URL the runner fetches; the Portal renders the harness with the same renderer that produces the runner's `bento.yaml` (the DataSource input replaced by the sample, the output replaced by the Portal's own capture route, one message), creates it as an ephemeral stream on the project's pipeline runner through its streams API, waits at most three seconds, deletes the stream whatever happened, and answers `input` (what the sample parsed to), `mapping` (every message the processors produced), `validation` (each message checked as an NGSI-LD entity, PF-42, and against the space's DataModel schema when it has one) and `errors` (the runner's lint errors with their line numbers, and a processor error with the message it failed on and the index into `spec.steps` of the step it failed at, which the harness stamps before every step and keeps at the first failure). The test MUST write nothing to Git, the broker or an endpoint, MUST run at most one test stream per project at a time, and MUST answer `503` when the project has no runner or it does not answer.
- **PL-44** [H] — The pipeline studio MUST offer the test on the manifest being edited and draw the trace as stages, an error underlined at its line in the mapping editor; and, from a dropped CSV or JSON sample, MUST draft the `DataSource`, the entity type and the Bloblang mapping from the sample's columns (a column named `id`, `identifier` or ending in `_id` as the local id, the rest as attributes) so the first test runs before anything is typed (UI-32, PL-01).
- **PL-47** [H][S] — The Portal reconciler MUST render every approved `Pipeline` whose `spec.source.dataSourceRef` names a `DataSource` of the project into one runner stream (the DataSource input of Architecture/08 §6; for an `http` DataSource a `generate` clock at `spec.period` followed by the `http` processor, because Bento's `http_client` input polls without pause; the inline mapping of PL-41, an `unarchive` step when the mapping yields an array so one poll writes many entities, and an output that upserts through `spec.targetEndpoint` with the project pipelines client by environment interpolation, PL-16), create or replace it over the runner's streams REST API (PL-09) and re-assert every rendered stream on each sync, so a restarted runner has them again within one sync interval; the target endpoint's slug comes from the `Endpoint` manifest's `spec.slug` in the mirror. `status.phase` is the runner's answer: `Live` while the runner runs the stream, `Error` with the runner's reason when it refuses it, `Pending` with a condition when no runner is configured. A Pipeline in Git the runner does not run MUST NOT show `Live`.
- **PL-48** [H] — The pipeline test (PL-43) MUST treat a mapping that yields an array as one entity per element, the same `unarchive` PL-47 renders, capped at 20; and when the candidate's source is an `http` DataSource the studio MUST offer that DataSource's own URL as the sample (`sample.url`, fetched by the runner), so the first test runs on the live feed without a file.
- **PL-49** [H] — The studio MUST NOT propose a `bloblang` pipeline whose mapping has not passed the test since it last changed: Propose is disabled with the reason on the form and on the YAML view alike, and the test's green answer is tied to the mapping text it ran (UI-47).
- **PL-51** [P][S] — The reconciler MUST render an endpoint-sourced pipeline whose `spec.source.trigger.subscription` names a type and `watchedAttributes` as a change-gated stream: a clock at the pipeline's `period` (10 seconds when absent, never under 5) reads the source page with the query's attributes and the watched ones, a hash of every entity's id and watched values is compared with the hash the stream last passed, kept per stream in the runner's shared `pipeline_changes` cache, and the page reaches the compute only when the hash differs, so the compute runs once per change of a watched value and the first page after a runner restart always passes; the runner's shared resources MUST declare that cache.
- **PL-50** [P][S][H] — A `DataSource` MAY name any input the pinned runner ships as `spec.type` (the list jc-core holds, read from the runner image; a name outside it MUST be refused with the list), except the inputs that work on the project's runner instead of reading a feed, which MUST be refused at the top and inside a wrapper input alike: `subprocess` and `stdin` (a program, the runner's own input), `kubernetes_watch` (the cluster API as the runner's ServiceAccount), `inproc` and `resource` (another stream of the runner), and `dynamic`, `http_server` and `socket_server` (an API or a listener in the runner's pod; a feed that pushes writes to an Endpoint). An input nested in `broker`, `sequence`, `batched` or `read_until` MUST meet every rule of a top-level one, an input's own `processors` MUST meet the rules of a PL-52 step, and the Bloblang anywhere in `spec.input` (a `generate` mapping, a `${! … }` field) MUST meet the PL-16 host rule (T-3833). It MUST then carry that input's own configuration as `spec.input`, verbatim in the input's field names; every field the runner documents as a secret MUST hold exactly one `${VAR}` interpolation naming an `envVar` of `spec.secrets` (`{ name, key, envVar }`, MF-35, PL-16), a literal there being refused, and every other `${VAR}` in `spec.input` MUST also name an `envVar` of `spec.secrets`, so a manifest never reads the runner's own environment, and a password inside any connection string (`user:password@`, `password=`) MUST likewise be such an interpolation; the reconciler MUST render `input: { <type>: <spec.input> }` unchanged and inject the named secrets (PL-15); a file-reading input, and `fsevent`, which watches paths, MUST name paths under `/data/`, the runner's files volume; an input that terminates on its own MAY back a `scheduled` pipeline and a broker or socket input MUST be `resident` (PL-04). The Portal's Data Sources form MUST offer the runner's inputs grouped for an operator with the runner's one-line summary each, and a configuration form generated from the input's field tree with secret fields as `secretRef` pickers (UI-32).

## 12. Sources, steps and outputs

A Pipeline takes the shape Bento runs: inputs, an ordered list of processors, outputs ([ADR-N-023](../Decisions/adr-n-023-pipeline-sources-steps-outputs.md)).

- **PL-52** — A `Pipeline` at `joinedcontext.com/v1alpha2` MUST carry `spec.sources` (one or more; each a `dataSourceRef`, or an `endpointRef` with a `query` or a `trigger` as PL-31 and PL-42 describe), `spec.steps` (an ordered list, possibly empty; each step exactly one of a PL-33 compute kind with its fields, a `mappingRef`, or `processor: { <name>: <config> }` naming a processor the pinned runner image ships, verbatim in the processor's field names, a name outside the list jc-core holds being refused with the list; `command` and `subprocess` are not on that list, because they run programs inside the project's shared runner, nor are `awk`, `javascript` and `template`, because each reads the runner's files or environment from inside a step (`awk`'s `getline`, `ENVIRON` and `system()`, `javascript`'s `require` and `bento.v0_fetch`, `template`'s Sprig `env`), and `wasm` stays the `wasm` compute kind of PL-34; the Bloblang anywhere in a step reads none of the runner's host functions (`file`, `file_rel`, `file_rel_json`, `hostname`, and `env` but for the variables the platform injects, T-3833)) and `spec.outputs` (one or more; each a `targetEndpoint` with an optional `mode` as `output.mode` has today); the order of `steps` is the order they run in, and the manifest stores no edges. A `v1alpha2` Pipeline MUST NOT carry `source`, `compute`, `output` or `targetEndpoint`.
- **PL-53** — The reconciler MUST render one source as that source's input (PL-47, PL-50, PL-51) and several as a Bento `broker` input whose `inputs` are the sources in order; the steps as `pipeline.processors` in order, after the processors each source's own input needs; one output as the upsert of PL-47 and several as a `broker` output with `pattern: fan_out_fail_fast` over them, so a failed write goes back to the input, which replays it to every output (each is an idempotent upsert), and never holds the stream where it cannot stop (T-2983). `branch`, `switch` and `workflow` MAY appear as steps, carrying their own processors in their configuration.
- **PL-54** — jc-core MUST read a `joinedcontext.com/v1alpha1` Pipeline as the `v1alpha2` Pipeline it means (`sources: [source]`, `steps: [compute]` or `[]`, `outputs: [{ targetEndpoint, mode }]`) and the stream rendered from either MUST be identical, byte for byte, which the reconciler's golden files prove; the envelope MUST accept `v1alpha2` for `Pipeline` and for no other kind; the Portal MUST write `v1alpha2` whenever it creates or edits a Pipeline that has a source, keeping every source, step and output its form does not show, and MUST NOT rewrite a `v1alpha1` Pipeline nobody edited; a Pipeline whose input lives only in its `bento.yaml` has no `sources` to write and stays `v1alpha1`.
- **PL-55** [S] — Admission MUST check the pipeline's ServiceAccount against every source's Endpoint for the read and every output's Endpoint for the write (PL-18…PL-20); each source's secrets MUST be injected under that source's own `envVar` names and a `${VAR}` of one source MUST NOT name another source's secret (PL-50); a `container` step MUST be the only step of a `scheduled` pipeline (PL-35); a `wasm` step MUST carry the pinned module digest of PL-34a.
- **PL-56** [H] — The pipeline studio MUST draw a Pipeline as one lane, sources on the left, the steps in order, outputs on the right, where a wire is drawn by hand but only ever sets that order: a wire from a node's output port to a step's input port moves the step behind that node, the last step feeds every output, and a wire the runner cannot run (into a source, out of an output, from a step that is not the last into an output) MUST be refused with the reason, so the manifest still stores no edges (T-3221); it MUST offer a palette of the runner's processors grouped by category with the runner's one-line summary each, insert the chosen processor as a step between two nodes, show the selected node's own Bento block as YAML (never another node's block and never a secret value, PL-17), and paint the test trace of PL-43 per step by the index of its processor.
- **PL-57** [P] — The reconciler MUST inject `JC_SPACE`, the rendered segment of the pipeline's target space (PF-84), beside `JC_ORG_DOMAIN`, and a mapping MUST build entity ids from the two (PF-44); a pipeline with several outputs gets one variable per output, named `JC_SPACE` for the first output and `JC_SPACE_2` for the second, the suffix counting on from there.

## 13. The workbench, validated writes and the log

The pipeline workbench and the rule that only valid records are written ([ADR-N-034](../Decisions/adr-n-034-pipeline-workbench.md)).

- **PL-58** [H][A] — The Portal MUST offer one pipeline workbench whose steps, in order, are source, sample, mapping, mapped output, validation, and target and save; each step MUST show its output and a one-line hint, and the schedule, batching and retries MUST sit folded behind "More options" with safe defaults (ADR-N-034, UI-84).
- **PL-59** [S] — A record MUST count as valid only when its type is a class of the target space's model (DM-61), its id follows PF-42 for that space, and its attributes satisfy the model's shape: closed unless the model is open (the NGSI-LD system members of DM-130 are never attributes, so a closed shape admits them), required present, single where not multivalued, of the slot's datatype, within its enum and of its NGSI-LD attribute kind; a refusal MUST name the constraint by its SHACL component and its path (DM-43).
- **PL-60** [S] — The reconciler MUST render, before the output of every pipeline whose target space has a model, a validation stage built from that model's artifacts at the version the space pins, MUST re-render it when that version changes, and a record the stage refuses MUST NOT be written (PL-59).
- **PL-61** [S] — A refused record MUST go to the pipeline's rejected list in the Portal database, newest 1000 kept per pipeline, holding the record with every secret-shaped value masked, the rule it broke and the time; the list MUST need read on the pipeline, and its "Retry after fix", which writes the records that now pass, MUST need `propose` on `Pipeline` (PL-25, PF-50).
- **PL-62** [S] — The runner MUST send one outcome line per record (pipeline, run, record id, step, outcome, message) through a sink that drops rather than retries, and the Portal MUST answer a pipeline's runs with their written, rejected and failed counts and each run's log, for that pipeline only, with read on it and never a token or a secret's value. ## 14. Stale-entity expiry

An entity whose source dropped it stays in the space with its last value until someone deletes it. A pipeline that reads a full snapshot MAY say that absence means removal. This age sweep guesses from silence; a pipeline whose source can say what exists or what was removed follows it exactly by `spec.sourceDeletes` (section 16).

- **PL-64** [S] — A Pipeline MAY carry `spec.expiry: { after, types }`: `after` a whole number of hours or days (`12h`, `14d`) from `1h` to `365d`, `types` one to twenty distinct entity types. Without it nothing is ever deleted automatically. With it, the reconciler MUST run one sweep per hour on the project's runner, as the pipeline's ServiceAccount through its output Endpoint, that deletes (`deleteBatch`) every entity of those types in that Endpoint's space whose `modifiedAt`, or `createdAt` when it was never modified, is older than `after`, and no other entity; a disabled pipeline sweeps nothing. The Portal MUST refuse the proposal when the pipeline has more than one output, when another Pipeline of the project writes into the same space, when a type is not a class of the space's model, or when no Policy grants the account `deleteBatch` and `queryBatch` on those types in that space, naming the Policy to extend; the grant is never widened for the author.
- **PL-65** [H] — The pipeline form MUST offer expiry off by default, with the window and the types, and say before saving what it deletes; the pipelines list and the pipeline page MUST state it in words ("Entities not updated for 14 days are removed") on every pipeline that has it.

## 15. Entity and attribute lifetime

A pipeline that knows when what it writes stops being true says so in the manifest, and the broker removes it at that moment (TS 104 175 4.22). Unlike the stale sweep of section 14, nothing is deleted by a second stream: the write itself carries the end time.

- **PL-80** [S] — A Pipeline MAY carry `spec.lifetime`, a list of one to twenty entries `{type, entity?, attributes?}`, each `type` distinct and a class of the target space's model that one of the pipeline's outputs writes, each entry carrying `entity`, `attributes` or both. `entity` MUST be exactly one of three modes: `{from: <field>, plus?: <duration>, notAfter?: <duration>}` sets the end time to the record's `field` plus `plus` (none when absent), and with `notAfter` to the earlier of that and the write time plus `notAfter`, or to the write time plus `notAfter` alone when the record's `field` is missing or not a date-time; `{rolling: <duration>}` sets it to the write time plus the duration at every write, a lease the next write renews; `{at: <instant>}` sets one fixed RFC 3339 instant with an offset. `attributes` is a list of at most 64 `{names, <one mode>}`, `names` one to 64 slots of `type` and no slot named in two entries. A `from` field MUST be a slot of `type` whose range is a date-time, or `observedAt`, the newest `observedAt` member among the record's attributes. A duration is ISO 8601 days, hours, minutes and seconds from `PT1M` to `P3650D`.
- **PL-81** [S] — Admission (PL-55) MUST refuse a lifetime entry whose `type` no output writes or the space's model does not declare, a name that is not a slot of `type`, a NGSI-LD system member (DM-130) in `names`, two modes in one target, a duration outside `PT1M`…`P3650D`, a `notAfter` without `from`, and an `at` that has already passed when the proposal is made, each with the entry's path and the rule it breaks.
- **PL-82** [S] — The rendered stream MUST compute each end time after the author's steps and immediately before the write, as RFC 3339 UTC with second precision, and write it as the entity's `expiresAt` or as the `expiresAt` member of each named attribute (DM-130); a mapping edit therefore never loses a lifetime, and the lifetime is never stored only in a mapping comment. A `from` field that is missing or not a date-time MUST write the write time plus `notAfter` as that target's `expiresAt` when the mode sets `notAfter` and no `expiresAt` when it does not, keep the record, and count the record in the run's outcome lines with the reason `lifetime-from` (PL-62); it MUST NOT drop the record silently. An end time already in the past is written as computed, and the broker removes it at once.
- **PL-83** [S] — Admission MUST refuse together a mapping that writes `expiresAt` itself (on the entity, or on an attribute) and a `spec.lifetime` for the same target, and an `entity` lifetime and a `spec.expiry` (PL-64) naming the same type, naming both places; an `attributes` lifetime MAY combine with either. Where several end times reach one entity, the broker's rule applies: the writer's `expiresAt` wins over the space rule **Current values** (DM-83).
- **PL-84** [S] — A lifetime MUST NOT widen a Policy. Removing data by its end time needs no grant beyond the write that set it, because the pipeline sends no delete: the broker drops the entity or attribute when its `expiresAt` passes, and a writer that may upsert an entity may already end it the same way under TS 104 175. The reconciler MUST therefore grant nothing for a lifetime (no `deleteBatch`, unlike PL-64), a Policy cannot forbid the `expiresAt` member (DM-131), and every removal stays declared by a manifest (DM-96).
- **PL-85** [H][S] — Before a Pipeline is proposed, the Portal MUST run its sample records through the verdicts of the write path and return them per record and field: the class, id and shape of the space's compiled model (PL-59), the target Endpoint's view and Policy (every type and attribute the record writes is writable there for the pipeline's ServiceAccount, judged without writing), and the lifetime each record would get (PL-80…PL-83). The verdict MUST be tied to a digest of the manifest, the model version and the Policy revision it ran on; the Portal MUST refuse a proposal without a green verdict on the same digests with `409`, naming the check to run again, and the editor MUST disable **Propose change** with the same reason, so a client that skips the editor is refused too (PL-49). The editor MUST offer the lifetime as four choices, whole entity from a field, whole entity after each write, whole entity on a fixed date, and only some fields expire, plus keep entities (no lifetime), and read each one back from `spec.lifetime`.
- **PL-90** [S][H] — A person who may propose a Pipeline MAY ask for its ServiceAccount's access to an Endpoint of another Context Space, in the same project or another one: an access request names the pipeline, the Endpoint (`{project, name}`), the operations (`read`: `retrieveOps`; or `write`: `upsertBatch`, `createBatch` and `queryBatch`, as a pipeline's own write grant holds), one to twenty entity types, each with one to fifty attribute names written out (no wildcard and no empty list, so a request never asks for "all"), an optional end date and a reason of at most 500 characters. The request MUST grant nothing: the Portal keeps it in the owning project's inbox (API/01 §48) and writes no manifest until an owner approves it. Before approval the requester MUST see the owning project's name, the Endpoint's name and the request's state, never the space's data or model; a request for an Endpoint the pipeline's account can already use for those operations, or a second open request for the same pipeline and Endpoint, MUST be refused with `409`, as MUST a request while the deployment runs streams under the project's shared `pipelines` account (PL-19), since a grant to it would reach every pipeline of the project.
- **PL-91** [S] — An owner of the Endpoint's Context Space (`approve` on its ContextSpace) approves or declines a request in the owning project. Approval MUST propose one Change into the owning project's repository, authored by the approver: the Endpoint's `allowedProjects` gaining the requesting project when the Endpoint's audience is `project-list` or `project` (an `organization` or `public` Endpoint keeps its audience), and one Policy `{endpoint}-{project}-{pipeline}` whose assignee is the `serviceAccount` `{project}/pl-{pipeline}`, whose `information` names exactly the requested types and attributes and whose `validity.to` is the end date. The Change MUST follow the owning project's lane and its four-eyes rule (T-4833); the person who filed the request MUST NOT approve it (`403 self-approval`), whatever rights they hold in the owning project. A declined request records the owner's reason, which the requester reads.
- **PL-92** [S] — A Policy assignee `serviceAccount` whose id is `{project}/{name}` MUST match only the account `{name}` of the project `{project}`; a bare `{name}` MUST mean the account `{name}` of the Policy's own project, and MUST NOT match an account of that name from another project the Endpoint admits. A grant written for a pipeline of another project MUST use the qualified form.
- **PL-93** [S][H] — Revoking an approved request MUST propose a Change that sets the Policy's `validity.to` to now and, when no other grant of the Endpoint names the requesting project, takes the project off `allowedProjects`; an end date passing ends the grant the same way at the gateway, with no Change. From then on the gateway refuses the pipeline's read or write (`403`); the pipeline's run log MUST record the refusal as "access revoked by {owner} on {date}" (or "access ended on {date}" for an expired grant), the pipeline MUST pause itself after three consecutive runs refused this way, and its owner MUST be notified with that reason.
- **PL-115** [S][H] — A person who may read an Endpoint MAY ask, on its page, for a read of one to twenty entity types it serves, for themself only, with an optional end and a reason of at most 500 characters (API/01 §48.1). The request MUST name no grantee and MUST come from a person's session, never a service account's or an agent's token (PF-58); it waits in the same incoming list as a pipeline's (PL-91), and approving it MUST propose exactly one Policy whose assignee is `user` with the requester's username, naming exactly the requested types, with the end as `validity.to`; the requester MUST NOT approve it (CC-34). A type the Endpoint does not serve and an end in the past MUST answer `422` naming the field.

## 16. When the source deletes a record

A record an open-data portal withdraws, a station a register drops or a bus that leaves the feed must leave the context space too, and only when the source really removed it: a source outage that answers an empty list must never empty the space. A pipeline says in `spec.sourceDeletes` how its source tells a removal, and the runner deletes only what that pipeline itself wrote.

- **PL-96** [S] — A Pipeline MAY carry `spec.sourceDeletes: {mode, misses?, maxShare?, deletedWhen?}`, `mode` one of `never`, `snapshot`, `events` or `lease`; absent means `never`, the behaviour of section 14 without `spec.expiry`. `misses` (1 to 10, default 2) and `maxShare` (1 to 100 percent, default 10) belong to `snapshot` only and `deletedWhen` to `events` only; a field of another mode, an unknown field or an unknown mode MUST be refused, naming the field.
- **PL-97** [S] — In `snapshot` mode the runner MUST count a run complete only when it read every page of the source without an error, a timeout or a refused record of the source's own format, and, when the source states a total, read exactly that many records; it MUST then compare the ids the run wrote with the pipeline's source ledger and delete an id missing from `misses` consecutive complete runs. An incomplete or failed run MUST delete nothing and MUST NOT count as a miss. A run that would delete more than `maxShare` of the ledger MUST delete nothing, MUST be held with the reason `share-exceeded`, and MUST alert the pipeline's subscribers (PL-71); a person with `approve` on `Pipeline` releases it once. The Portal MUST offer a dry run that lists, without deleting, the ids the next complete run would remove.
- **PL-98** [S] — In `events` mode the runner MUST evaluate `deletedWhen`, a Bloblang query held to the author rules of PL-50, on each mapped record after the author's steps, and for a record where it is true MUST delete the entity of that record's id instead of writing it; a `deletedWhen` that errors on a record MUST count the record as failed and delete nothing. In `lease` mode the pipeline sends no delete: the rolling entity lifetime of `spec.lifetime` (PL-80) ends the entity when the source stops renewing it, under PL-84.
- **PL-99** [S] — Admission MUST refuse `snapshot` on a pipeline without a `period` or a `schedule` or whose DataSource never ends on its own (`mqtt`, `websocket`, a broker or socket input), `events` without a non-empty `deletedWhen`, `lease` without a `spec.lifetime` entry whose `entity` is `rolling`, and any `sourceDeletes` together with `spec.expiry`, each naming the field. A `snapshot` or `events` pipeline MUST be refused until a Policy grants its ServiceAccount `deleteBatch` and `queryBatch` on the written types in the target space, naming the Policy to extend; the Portal never widens a grant for it, and every delete goes through the pipeline's output Endpoint and is judged and audited like any other write.
- **PL-100** [S] — Only an entity in the pipeline's source ledger, a row `(source key, entity id, first seen, last seen in a complete run, run id)` per pipeline that the runner writes on each write, MAY be deleted by `sourceDeletes`; who wrote an entity last MUST NOT decide it. Where several pipelines write attributes of one entity, each pipeline MUST write its attributes with the `datasetId` `urn:jc:pipeline:<name>`, a source delete MUST remove only that pipeline's attribute instances, and the entity MUST go only when no other dataset holds an attribute. An entity a person changed after the pipeline's last write MUST be reported in the run, not deleted. Each delete MUST be stored as a tombstone with `deletedAt` (DM-115) whose provenance carries the pipeline as actor and the reason `source-snapshot` or `source-event` (DM-111).
- **PL-101** [H] — The pipeline editor MUST offer the four choices in words (keep records the source removed, remove what complete runs no longer list, remove what the source marks as deleted, remove what the source stops renewing), say on `never` that removed records stay, show the misses, the share and the dry run for `snapshot`, and read each choice back from `spec.sourceDeletes`.

## 17. Indicators over several sources

A `kpi` step computes one indicator from up to five sources, each read with the pipeline's own grant, joined by the run's time window, by a shared entity or by an area, and written through the target Endpoint as one `KeyPerformanceIndicator` per run and per joined key ([Architecture/08 §3](../Architecture/08-pipelines.md#indicators-over-several-sources-pl-102pl-105)).

- **PL-102** [S] — A `v1alpha2` Pipeline MAY carry one step `{kind: kpi, kpi: {...}}` as its only step, over two to five `spec.sources`, each with a `name` (a DNS label unique among the sources, the input's name in the formula) and an `endpointRef` with a `query` of one `type`; `kpi` holds `name` (the indicator's `{localId}`, a DNS label of at most 48 characters), an optional `title`, `formula`, `unitCode` (the result's UN/CEFACT code) and `join` (`by: time`, the default, or `by: entity` or `by: area` with `keys`, one attribute per source naming the entity it describes or the area it lies in); a single-source KPI stays the PL-45 preset.
- **PL-103** [S] — `formula` MUST be arithmetic (`+ - * /`, parentheses, decimal numbers) over terms `sum(input.attribute)`, `avg(…)`, `min(…)`, `max(…)` and `count(input)`; admission MUST refuse, with the term and the rule, a name that is not a declared source or not in that source's `query.attrs`, an unknown function, a formula of more than 512 characters or 64 terms, a sum or difference of two terms whose units the space's model gives differently, and a `unitCode` other than the formula's own unit (dimensionless, `C62` or `P1`, for a ratio of equal units).
- **PL-104** [S] — The run MUST compute the formula over every source's page of the same run and write one indicator per run (`by: time`) or one per key present in every source (`by: entity`, `by: area`, at most 500 per run), the key's slug appended to `name`; `derivedFrom` lists every source Endpoint's URN and `calculationFormula` holds the formula followed by each source's input name, type, `q` and the number of rows it read, so the indicator needs no attribute beyond Architecture/03 §2. A division by zero, an `avg`, `min` or `max` over no values, a source that answered with an error (a lost grant is a `403`) or did not answer MUST write nothing for that run and record the reason as the run's failed line (PL-62); a partial value is never written as if complete.
- **PL-105** [S][H] — The Portal's KPI editor MUST let a person build a KPI without writing Bloblang: sources picked from the Endpoints the pipeline's account can read (a source it cannot read offers the PL-90 request), the join and a formula picked from plain choices (count, sum, average, share of two sums, per area, per entity), a typed formula only under **Advanced**, each field checked as it is typed with the reason in words, and a preview of the value on the current pages of the sources before the Pipeline is proposed.

## 18. History rows per attribute

How a pipeline's writes become history rows (DM-104…DM-109) is a choice per written attribute, made in the manifest beside `spec.lifetime` and never only in a mapping: the person picks what to keep and where the time of a row comes from, and the Portal says before a proposal whether the space and the broker can keep that promise.

- **PL-106** [S] — A Pipeline MAY carry `spec.history`, a list of one to twenty entries `{type, attributes}`, each `type` distinct and a type one of the pipeline's outputs writes, `attributes` one to 64 entries `{names, keep, heartbeat?, observedAt?}`. `names` are one to 64 slot names of `type`, none a NGSI-LD system member (DM-130), and a name appears in one entry of its type only. `keep` MUST be one of `every` (a row per measurement, the space rule `record: every`), `changes` (a row when the value changes and once per `heartbeat`, `record: onChange`, DM-109) or `latest` (the current value only, no rows). `heartbeat` MUST be present with `changes` only, a duration from `PT1M` to `P3650D`. `observedAt` MAY name a date-time slot of `type`, whose value becomes the `observedAt` of each named attribute, or be `received`, which removes the mapping's `observedAt` so the broker stamps the receive time (DM-107); absent, the mapping decides.
- **PL-107** [S] — The rendered stream MUST set each planned `observedAt` after the author's steps and before the lifetime step (PL-82), on every instance of each named attribute the record carries, as RFC 3339 UTC; a slot whose value is missing or no date-time MUST leave the attribute without `observedAt` and keep the record.
- **PL-108** — The reconciler MUST write `keep: every` and `keep: changes` into the space's retention document (DM-82) as the attribute's `record` and `heartbeat`, unless the space's own rule names a recording for that attribute, which wins; two pipelines of one space that plan one attribute differently MUST leave it to the space's rule. `keep: latest` writes nothing: the broker keeps history per type (DM-97), so it holds only where the type's history is `off`.
- **PL-109** [S] — The record check (PL-85) MUST refuse, naming the attribute and the rule, a plan the space or the broker cannot keep: `latest` for a type whose history is not `off`; `every` or `changes` for a type whose history is `off`; `every` with `observedAt: received`, or with sample records whose attribute carries no `observedAt` (each write a new row, DM-104); a plan other than the space's own recording of that attribute; a plan other than another pipeline's of the same space for that attribute; and an `observedAt` slot whose sample value is no date-time.
- **PL-110** [S] — A history plan MUST NOT widen a Policy: it changes rows only of attributes the pipeline writes through its own Endpoint, it is changed only by a change to the Pipeline, which needs the Pipeline's write grant (PL-55), and the editor's History column MUST show names, choices and sources only, never a sample value of a slot the model marks personal.
- **PL-111** [S] — `jcctl validate` MUST refuse, as an error naming the file, a permission Policy that grants a write of context data and that no Endpoint of its project binds (same space; named by `policyRef`, or no `policyRef`; an App's own Endpoint only its own grants), and a Pipeline output whose `targetEndpoint` the project does not declare or that does not bind the output's derived write Policy (PL-20), saying which Endpoint refuses it and why ([ADR-N-057](../Decisions/adr-n-057-policy-rules-policy-refs-authzen.md) decision 5, T-5035).
- **PL-112** [S] — A `v1alpha2` Pipeline step `{kind: datacube, datacube: {wholeArea, datasetPage, cubes}}` MUST render, through jc-core, into the one JSON-stat 2.0 decoder that writes one KeyPerformanceIndicator per numeric cell; `cubes` maps each table code (`[a-z]{2}[0-9]{4}[a-z]{2}`, one to 16) to `source` (https), an optional `update` date and the dimensions of the roles `period`, `area`, `indicator`, `unit` and `keys`; jc-core MUST refuse an unknown member or a parameter outside its pattern, naming the field, and a converted pipeline MUST render the mapping it ran before byte for byte, so its entity URNs stay (T-5295).
- **PL-113** [S] — An `http` DataSource MUST bound the response body it reads (`spec.http.maxBytes`, in bytes, 1 to 268435456; 33554432 (32 MiB) when absent), and the runner MUST refuse a body larger than the bound before any step of the pipeline sees it, logging the size and the bound at ERROR in the run log; a value outside the range MUST be refused as an error naming `spec.http.maxBytes` (Architecture/08 §6, T-5355).
- **PL-114** [H] — An `http` DataSource MAY set `spec.http.format: csv`; the runner MUST then hand each poll's body to the pipeline's steps as one message per CSV row, keyed by the header's column names (Bento `unarchive: csv`, the shape the `csv` input sends), and without `format` MUST hand the body over as one message; the pipeline test (PL-43) and the workbench sample of a pipeline reading that DataSource MUST split the source's sample the same way, so a mapping that passes the test sees the messages the live run sends (Architecture/08 §6, T-5350).
