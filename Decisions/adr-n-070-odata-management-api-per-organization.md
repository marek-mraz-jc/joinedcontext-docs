# ADR-N-070: OData as the Management API, One Service per Organization

Date: 2026-11-12  
Status: Proposed  
Supersedes: [ADR-N-063](adr-n-063-one-api-style-no-graphql.md) for the control plane (its option B, §3.2 and the last bullet of §5); its data-plane, agent and no-GraphQL decisions stand  
Decision Makers: product owner (2026-11-08: "all APIs ... should be odata"; 2026-11-12 supervisor session: "one task ... based on the architecture and multi organization to rewrite professionally to odata, full frontend, backend, e2e test", "with proper policies"); drafted by worker-t6809 (T-6809), owner may override

This record makes OData 4.01 the one API of the control plane: every Organization is one OData service at `/{org}/api/v1/`, generated from the operation registry, read as entity sets and functions, and written through actions; a configuration write is an action that opens, plans or decides a reviewed Change. [API/13](../API/13-api-conventions.md) carries the rules in detail and [API/15](../API/15-addresses-v1.md) the address. The research that compared OData with GraphQL is [Research/next-platform/08](../Research/next-platform/08-management-api-and-testing.md).

## 1. Context

- **Two query styles.** The Portal serves about 280 REST route strings and its UI calls about 400 distinct `/api/v1` paths (jc main `75e834b`, 2026-11-12). Lists page three ways and filter four ways (ADR-N-063 §1); API/13 unified the parameters but each route is still learned one by one.
- **OData is already built here.** Antares ships `odata-url` (a bounded URL parser), `odata-csdl`, `odata-json` and `odata-table` (one evaluator over memory, Postgres and Git sources, T-6642, T-6659). The Portal serves one OData service per project from the operation registry (`src/api/odata.rs`, T-6632, T-6655), the SDK grid reads it (T-6644) and the Endpoints list draws from it (T-6645). shako, the forge, answers every Portal call over OData (`crates/shako/PORTAL-ODATA.md`).
- **The reason ADR-N-063 gave.** It refused OData on configuration because "OData's metadata and batch model do not fit Git-backed reviewed writes". That holds for OData's direct writes (`POST` to a set, `PATCH`, `PUT`, `DELETE` of an entity, `$batch` change sets): each assumes the write lands when the request returns. A configuration write here is a Change that a person or a rule approves later. OData's actions fit it: an action is a named operation with typed parameters and a typed result, so `propose` returning a Change is an ordinary action.
- **Several Organizations per installation** ([ADR-N-058](adr-n-058-several-organizations-per-installation.md)). API/15 fixes `https://{host}/{org}/api/v1/` as the management API's root and its payload as OData.

## 2. Decision

1. **One service per Organization.** The service root is `/{org}/api/v1/` (API/15 §2): the service document there, the model at `$metadata` (CSDL XML, and CSDL JSON for `?$format=application/json` or `Accept: application/json`). The Organization is decided once per request, in one of three deployment modes: a shared host with the Organization id as the first path segment, a host bound to one Organization whose root maps to `/{org}/`, or a single-Organization deployment with the path segment off. Never from a header, a query option, a key value or a URN ([ADR-N-041](adr-n-041-entity-identity-is-space-and-urn.md), ADR-N-058). An unknown Organization id, and a path Organization on a host bound to another, answer `404` with the unknown-path body; a token or session of Organization A sent to B's root answers `401`. Installation-scope sets (installation Roles and RoleBindings, the list of Organizations) are served only at `/-/api/v1/`, to operators. The per-project service `/api/v1/projects/{project}/odata/` stays as a compat alias of the project's navigations until an API/10 notice ends it.
2. **Reads are entity sets, singletons and functions.** `projects` is an entity set keyed by `name`. Each project-scoped kind is a navigation of a project, `projects('{project}')/endpoints('{name}')`, which key-as-segment addressing writes as `projects/{project}/endpoints/{name}`, today's REST path. Each kind is also an organization-wide set with the composite key `(project,name)`, `endpoints(project='air',name='counters')`, for the organization pages (PF-61). Organization-scoped kinds (`roles`, `rolebindings`, `groups`, `members`) are sets of the service; the Organization and the caller (`me`) are singletons. Set names are the kind's REST plural, so the path shape does not move. A read-only operation with arguments (a search, a computation, a status) is an OData function. [API/13 §2b](../API/13-api-conventions.md#2b-operation-classes) assigns every registry operation its class.
3. **Configuration writes are actions that open a Change.** There is no `POST` to a set, no `PATCH`, `PUT` or `DELETE` of an entity, and no deep insert: each answers `405` with an error that names the action to call. An operation of the Change-proposing class (API/13 §2b) is an action whose name is the registry operation that runs it: bound to the entity it changes when one exists (`…/endpoints('counters')/JoinedContext.Portal.propose_update`, `…/propose_delete`, `changes('42')/JoinedContext.Portal.approve`, `…/reject`, `…/apply`), unbound or bound to its project for a create. Each returns the Change it opened or decided. A propose action takes `dryRun` and then answers the plan without opening a Change (API/13 §5). Lanes, four-eyes and auto-approval run unchanged inside the operation ([PF-52](../Requirements/platform.md), PF-58, PF-70, PF-71). An operation of the other action class (a run, a draft, a workspace or preview session, a token, a test or dry-run computation, a person in the identity provider, a data write through an Endpoint) is an action too and keeps its registry permission and lane; it opens no Change because it changes no configuration in Git.
4. **Concurrency and caching.** Every entity carries `@odata.etag`: a hash of the caller-visible projection of the entity and its revision, so a change to a property the caller cannot see does not move their tag. A bound action that changes an existing entity, or decides a Change, requires `If-Match`: absent is `428`, stale is `412` with the current ETag, and no Change is opened. A create takes none. The ETag is compared only against an entity the caller may read; otherwise the action answers `404` as an unknown key does. Answers carry `Cache-Control: private` and `Vary: Authorization, Cookie`; a `304` to `If-None-Match` comes only after the authorization check.
5. **Query options.** Every entity set honours `$filter`, `$select`, `$orderby`, `$top`, `$skip`, `$count` (and `/$count`), a key, `$expand` of one level on a navigation `$metadata` declares, and server-driven paging. Nested `$expand` options, property paths and `$count` pass the same readable-property check. The server refuses, and never ignores:
   - `501`: `$apply`, `$search`, `$compute`, `$levels`, `$deltatoken` and delta links, the lambda operators `any` and `all`, `/$ref`, `/$value`, `$batch` (the endpoint exists only to say so), and any function or action the model does not declare;
   - `400`: `$expand` deeper than one level or on a property that is no navigation, `$top` or `$skip` above the limits of item 6, an unknown or repeated system query option, and a property, function or type the caller's `$metadata` lacks. A hidden property, an unknown one and one of another Organization answer a byte-identical `400` body, so a `$filter` is never an oracle;
   - `406`: a `$format` or `Accept` other than JSON for data, XML or JSON for `$metadata`.
6. **Limits are deployment-wide.** One settings block, with no per-Organization field: `odata.page_max` 1000 rows a page (`Prefer: odata.maxpagesize` lowers it), `odata.read_max` 10,000 readable rows evaluated per request (past it `400` asking for a narrower `$filter`, never a cut set), `odata.skip_max` 10,000, `odata.filter_max_nodes` 64, `odata.filter_max_depth` 8, `odata.expand_depth` 1. `$filter`, `$orderby` and `$count` run only over readable rows and properties.
7. **Paging.** `@odata.nextLink` carries an opaque `$skiptoken`, MAC-signed over the Organization, the caller, the set, a hash of the query and an expiry; a replayed, tampered, expired or other caller's token answers `400` or `404`. Each page runs the authorization again and fills with readable rows only. The link's base comes from the host registry or the path root, never from `Host` or `X-Forwarded-Host`.
8. **Errors.** An OData request gets the OData error object, `Content-Type: application/json`, whose `code` is the [API/09](../API/09-errors.md) problem type and which carries its Problem Details members and the request's `trace_id`: `{"error": {"code": "https://…/precondition-failed", "message": "…", "target": "spec.audience", "details": [ … ], "title": "…", "status": 412, "trace_id": "…"}}`. A REST compat request keeps `application/problem+json` (RFC 9457) with the same `type` and `trace_id`. `message` says what the caller can do next and never echoes a secret.
9. **Policies decide every set, property and action.** One authorization path serves OData, REST compat and MCP: the registry's `Caller::grants` and `Effective::may` / `Effective::may_read_manifest`, before any query option is read.
   - Roles and RoleBindings at installation, organization and project scope (PF-56), `projects.visibility` (PF-61), `projects.creation` (PF-65) and organization members' read of internal datasets ([ADR-N-067](adr-n-067-organization-members-read-internal-datasets.md)) decide which rows a set holds. A set never lists, counts or expands a row of another Organization or one the caller may not read: `$count` counts readable rows, an unreadable key is `404`.
   - An Endpoint Policy and its attribute capabilities ([ADR-N-066](adr-n-066-attribute-capabilities-in-a-policy.md)) decide what a set showing data or Endpoint metadata answers.
   - A scoped connector token ([ADR-N-064](adr-n-064-scoped-connectors.md)) sees and calls only its project or segment.
   - People data is minimised ([ADR-N-061](adr-n-061-group-members-without-personal-data.md)): `members` carries no e-mail or personal property for a caller without `people-admin`, in `$metadata` and in rows; `people` (`jc_person_list`) is served to `people-admin` only and holds only that Organization's members.
   - `$metadata` and the service document are built per caller from `Effective`: they list only the sets, properties, navigations and actions the caller may use, so a viewer's model holds no write action, and no `secretRef`, `sourceUrl` or personal property appears in any. The anonymous caller gets `401`, unless the Organization has an Endpoint with `spec.audience: public`; then it sees only the public sets (PF-71).
   - An action on `Role`, `RoleBinding`, `Policy` or the `Organization` opens a red-lane Change that an `org-admin` other than its author approves (PF-58).
10. **Sessions per Organization.** In path mode every Organization shares one origin, so the session cookie and the CSRF token are bound to the Organization (cookie `Path=/{org}/`, and the Organization claim checked on every request): a valid cookie and CSRF token of Organization A sent to B's root are refused.
11. **MCP calls the same operations.** A `tools/call` runs the registry operation the matching OData request runs, with the same Organization rule and the same checks.
12. **REST stays as compat, frozen.** Today's REST routes stay thin wrappers over the same operations and answer today's bodies until an [API/10](../API/10-api-change-policy.md) notice ends them. Under `/{org}/api/v1/` a request is OData when it sends `OData-Version` or `OData-MaxVersion`, any `$` system query option, or names `$metadata`, the service document, a function or an action; otherwise it is a REST compat request. Answers carry `Vary: OData-Version, OData-MaxVersion` beside item 4's. No route, parameter or body is added to REST.

## 3. Alternatives considered

- **Keep ADR-N-063 (REST for configuration, OData for data only).** Two query languages for one client, and every new kind adds REST routes the UI learns by hand. Refused by the owner's order.
- **OData with direct writes** (`PATCH` merges the manifest, `$batch` change sets). Each direct write would have to return `202` and a Change in place of the entity the standard promises, so standard clients would misread every write, and a change set would mix approved and pending writes. Refused; actions say what happens.
- **One service per project** (T-6655's shape). An organization page (every Endpoint, every Change waiting for me) would need one call per project, and `$expand` could not cross a project. Kept only as an alias.
- **GraphQL.** Refused again for ADR-N-063's reasons: a second authorization layer per field, client-set query cost on one node, writes that are Git reviews.

## 4. Security

- No configuration write outside a reviewed Change, and no OData verb that pretends otherwise; an action of the other class keeps the permission and lane the registry gives it today.
- `$batch` off, `$expand` one level, page, rows read, `$skip` and filter size capped by one deployment-wide settings block: a request's cost is set by the server, the same for every Organization.
- The Organization is decided once from the path or the host; a key, a URN or a header naming another Organization reaches nothing (`404`), and a token, a session cookie or a CSRF token of another Organization is refused.
- Per-caller `$metadata` is the field-level control: a property the caller may not read does not exist for them, in `$select`, `$filter`, `$orderby` and `$expand` alike, and its refusal is byte-identical to a misspelt name's.
- A `$skiptoken` is signed for one caller and one query and re-runs the authorization on every page; the `nextLink` base never comes from a request header.
- Every OData route has its line in the Portal's `authz_matrix` and `route_coverage` tests; a new action without one fails CI.

## 5. Consequences

- API/13 §2a describes the service; API/15 §4 points here.
- T-6809 builds it in slices: S1 this record, API/13 and API/15 with the operation class table; S2 the per-Organization root, `$metadata`, Organization resolution, isolation and cookie tests; S3 the policy parity matrix (every PF-56 role × every set and action equals the REST answer), per-role `$metadata`, `nextLink` and ETag; S4 functions, composite keys and the operations not mapped yet; S5 the SDK generated from `$metadata` with a no-diff check; S6 onward the UI by page group, under a ratchet of the REST path count; the last slice e2e in the three modes, k6, screenshots and dead-code removal.
- The UI's REST gate is a Playwright capture of every journey's requests (each `/api/` request matches the OData grammar or a named allow-list: OIDC, MCP, SSE and WebSocket, uploads) and a static check that allows one fetch helper.
- The per-project `endpointList` set's `PATCH` and `DELETE` by key (T-6645) become `propose_update` and `propose_delete` actions; the old verbs stay until the UI moves.
- A request for a new REST route, for GraphQL or for OData direct writes is answered with this record.
