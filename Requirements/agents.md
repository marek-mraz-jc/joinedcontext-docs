# Agent Governance & Model Context Protocol

Family **AG** (AG-01…AG-85; AG-82 is unassigned). Owning chapters: [Architecture/07-agents-and-mcp.md](../Architecture/07-agents-and-mcp.md) and [Architecture/19-agent-runner.md](../Architecture/19-agent-runner.md). Verified by: [Testing/06-security-tests.md](../Testing/06-security-tests.md).

## 1. Identity, Authentication, and Scoping

- **AG-01** [A] — Every AI agent interacting with the platform MUST operate under an individual, auditable identity (Keycloak service account or an end-user delegated session via OAuth 2.1 Token Exchange RFC 8693) without generic shared bot accounts (CC-44).
- **AG-02** [A] — An AI agent MUST authenticate against platform endpoints using standard OAuth 2.1 Bearer tokens containing DPoP proofs.
- **AG-03** [A] — An agent's access rights across data entities and configuration manifests MUST be governed strictly by standard `Policy` entities and Git repository permissions without ambient superuser access.

## 2. Dual MCP Surfaces

- **AG-04** [A] — The platform MUST expose two separate, strictly decoupled Model Context Protocol (MCP) Streamable HTTP surfaces: the Data MCP Façade and the Configuration MCP.
- **AG-05** [A] — The Data MCP Façade MUST determine the active Context Space exclusively from the URL path or verified token audience, rejecting space names supplied as arbitrary tool arguments (SP-14).
- **AG-06** [A] — The Configuration MCP MUST reject direct write operations to the broker, gateway, or database, submitting all proposed modifications as Git merge requests (CC-46).

## 3. Tool Annotations and Elicitation Protocol

- **AG-07** [A] — All tools exposed across both MCP surfaces MUST declare accurate behavior annotations in their schemas (`readOnlyHint: true` for queries; `destructiveHint: true` for deletions and mutations).
- **AG-08** [A] — Any MCP tool execution involving high-risk operations or Red-lane configuration changes MUST invoke the MCP Elicitation Protocol, returning an interactive confirmation request containing an action description, plan diff, and confirmation parameters (CC-63).
- **AG-09** [H][A] — Elicitation confirmation requests MUST be surfaced within the Portal UI under Pending Agent Actions, allowing human approvers to review, approve, or reject the operation (CC-34).

## 4. Approval Lanes and Automation Boundaries

- **AG-10** [A] — Automated changes proposed by an agent via the Configuration MCP `propose_change` tool MUST be classified into interaction lanes per CC-63 (Green auto-approved, Yellow domain review, Red full review).
- **AG-11** [A] — An agent MUST NOT have the capability to approve its own merge requests or alter the approval lane configuration (CC-70).

## 5. Result Grounding and Verification

- **AG-12** [A] — All responses returned by the Data MCP and Configuration MCP tools MUST be structured and deterministically grounded, including evaluated Git commit hashes, UTC timestamps, and explicit drift indicators (CC-47).
- **AG-13** [A] — If a tool invocation is constrained or narrowed by policy enforcement, the response MUST include structured restriction metadata (`restricted: true`) without leaking forbidden data (R20, R22).

## 6. Sandboxes and Ephemeral Workspaces

- **AG-14** [A] — An agent with developer or analyst roles MUST be permitted to instantiate unmanaged, ephemeral sandbox spaces instantly via Green-lane blueprints (CC-67).
- **AG-15** [A] — Ephemeral sandbox spaces MUST carry metadata indicating `unmanaged: true` and an explicit expiration timestamp, excluded from automated drift detection runs (CC-21).
- **AG-16** [A] — Promotion of artifacts developed within an agent sandbox into durable, managed configuration MUST be conducted exclusively through the export and adopt workflow (CC-22, CC-68).

## 7. Attribution and Auditability

- **AG-17** [A][S] — Every Git commit generated by an agent MUST be author-attributed to the agent's unique identity.
- **AG-18** [A][S] — If an agent action was initiated by a human prompt or interactive command, the commit message MUST include a `Co-Proposed-By` Git trailer identifying the initiating user.
- **AG-19** [A][S] — All MCP tool invocations, inputs, results, and policy decisions MUST be logged within the central audit trail with correlation IDs matching the outer task context (R42).

## 8. Prompt Injection Defense and Boundary Hardening

- **AG-20** [S] — Data payloads ingested from external sources or queried from context entities MUST be treated strictly as untrusted data literals rather than executable system instructions.
- **AG-21** [S] — The MCP server MUST sanitize and validate all tool parameters against published JSON Schema draft-07 definitions before passing them to internal platform components.
- **AG-22** [S] — An agent MUST NOT be granted access to the underlying Kubernetes API, container runtime sockets, or local host filesystems.

## 9. Agent Runner Addon and Execution Limits

- **AG-23** [A] — The optional Agent Runner addon SHALL deploy a sandboxed OpenHands Software Agent runtime communicating exclusively over the network with the Data MCP and Configuration MCP endpoints.
- **AG-24** [A][S] — The Agent Runner deployment MUST enforce the `ConfirmRisky` policy, mapping high-risk operations directly to MCP elicitation prompts.
- **AG-25** [A][S] — The platform MUST enforce computational and rate limits per agent identity, including token-bucket limits on MCP requests, maximum concurrent tool executions, and step limits per autonomous plan.
- **AG-26** [A][S] — The Agent Runner MUST offer two profiles: `steward` (MCP only, no internet) and `builder` (MCP plus coding tools in an ephemeral workspace: shell, `cargo`, `pnpm`, `git`, test runners, headless browser); `builder` internet egress MUST pass through the platform egress proxy with a per-organization allow-list and per-request logging under the agent identity.
- **AG-27** [A][S] — A `builder` workspace MUST hold no token for real context spaces; it MUST receive only the sandbox endpoint of the app under construction and a forge token scoped to `apps/{name}/` on that app's branch.
- **AG-28** [A] — Builder workspaces MUST be destroyed after each build loop or at the AG-15 expiration, whichever comes first; nothing survives a workspace except its commits.

## 10. Data MCP Operation Coverage and Remote Access

- **AG-29** [A] — The Data MCP tool catalogue MUST cover every CIM 009 read and temporal operation the Endpoint's enabled representations expose, so no read a REST client can perform lacks a tool (EP-05, EP-24).
- **AG-30** [A] — Temporal tools MUST accept the NGSI-LD temporal query grammar (`timerel`, `timeAt`, `endTimeAt`, `lastN`, `aggrMethods`, `aggrPeriodDuration`) unchanged and evaluate it under the same policy decision as the REST temporal path (EP-07).
- **AG-31** [S] — The Data MCP MUST validate every tool argument against that tool's published JSON Schema draft-07 definition before it builds any broker request, rejecting unknown fields as a tool error (AG-21).
- **AG-84** [A] — Every query parameter the Endpoint's NGSI-LD read surface accepts MUST be an argument of the MCP tool that maps to the same CIM 009 operation, under the same name, with the same meaning and the same refusal; the names, JSON types and bounds MUST come from one table the REST surface and the Data MCP share ([Architecture/07-agents-and-mcp.md#the-shared-read-parameter-table-ag-84](../Architecture/07-agents-and-mcp.md#the-shared-read-parameter-table-ag-84)), and a parameter the gateway or the broker does not serve yet MUST be refused in the words of the REST refusal rather than accepted and dropped (AG-29, EP-24).
- **AG-85** [S] — A tool argument MUST NOT widen what a token reads: for the same request and the same token, the entities, attributes and members an MCP answer carries MUST equal what the REST surface answers, and a projection argument (`attrs`, `pick`, `omit`, `join`, `options`, `lang`, `count`) MUST NOT reveal a member, a linked entity or a total the REST answer withholds (EP-47, SP-16, SP-20).
- **AG-32** [A][S] — The Data MCP route MUST publish OAuth 2.0 protected-resource metadata (RFC 9728) and answer a call that needs a token with `401` and a `WWW-Authenticate: Bearer resource_metadata=…` header; on an Endpoint with `audience: public` the read tools MUST answer without a token, as the other representations do (EP-16, PF-45, PF-46).

## 11. Ephemeral Workspace Isolation and Credential-Free Execution

- **AG-33** [A] — The Agent Runner MUST create one ephemeral workspace per run and MUST destroy it when the run leaves a running state, at the profile's wall-clock limit, or at the sandbox expiry of AG-15, whichever comes first.
- **AG-34** [A][S] — A workspace MUST NOT carry a Kubernetes service-account token, a mounted Secret, a kubeconfig, or any platform credential; its only configured peers MUST be the agent proxy and the cluster DNS resolver.
- **AG-35** [S] — The platform MUST hold every credential a run needs (model provider, context endpoint, forge) and MUST inject it per request in the agent proxy, never handing it to the workspace.
- **AG-36** [S] — The agent proxy MUST authenticate a workspace by a per-run ticket that is stored only as a hash, is valid only while the run is running, and MUST additionally verify the mesh workload identity when the service mesh is enabled.

## 12. Credential Proxy Surface and Request Scoping

- **AG-37** [S] — The agent proxy MUST derive the target of every request from the run record: the endpoint slug, the repository, the branch, and the path prefix MUST NOT be supplied by the workspace.
- **AG-38** [S] — The agent proxy MUST strip inbound `Authorization`, `Cookie`, `NGSILD-Tenant`, `X-Userinfo`, and `X-Access-Token` headers from every workspace request before injecting its own.
- **AG-39** [S] — The agent proxy MUST refuse a write operation on the data route unless the run record allows writes, and MUST refuse any forge write outside `projects/{p}/apps/{app}/` on the run's own branch.
- **AG-40** [S] — The agent proxy MUST NOT return an injected credential, a `Set-Cookie` header, or an upstream authentication challenge to the workspace.
- **AG-41** [A][S] — The agent proxy MUST enforce, per run, the profile's limits on requests per minute, concurrent requests, response bytes, model tokens, and wall clock, and MUST end the run when one is exhausted.
- **AG-42** [A][S] — Every proxied request MUST be logged with run id, agent identity, initiating human, upstream, method, path, status, byte count, and duration, and MUST NOT log the injected credential or the request body of the model route.

## 13. Run Lifecycle, Human Interview, and Streaming Events

- **AG-43** [A] — A run MUST record its initiating user, the prompt, the prompt digest, the chosen endpoint, the confirmed data needs, and the profile, and MUST expose them unchanged for the life of the run.
- **AG-44** [A][H] — The runner MUST be able to ask the initiating user a question as a structured form (JSON Schema draft-07) and MUST NOT continue past a question marked as required until the user answers or the run expires.
- **AG-45** [A][H] — Run events MUST be streamed to the Portal in order, MUST carry a monotonic sequence number, and MUST be resumable from a sequence number after a dropped connection.
- **AG-46** [S] — A run event MUST be accepted only for the run whose ticket authenticated the request, and event content MUST be treated as untrusted data when rendered.

## 14. Agent Profiles, Tooling, and Cost Governance

- **AG-47** [A] — `kind: AgentProfile` MUST declare the runtime image, the model, the limits, the egress allow-list, the enabled tools, and the profile role (`steward` or `builder`), and MUST be an organization-scoped manifest under configuration as code.
- **AG-48** [A] — A run MUST reference exactly one `AgentProfile`; an installation without an `AgentProfile` for the `builder` role MUST NOT offer application generation.
- **AG-49** [S] — The runner image MUST be pinned by digest and signed, MUST run as a non-root user with a read-only root filesystem, and MUST declare resource requests and limits.
- **AG-50** [A][S] — The agent MUST NOT reach a network host that is not the proxy; package and documentation access MUST pass through the proxy's allow-listed package route with a per-run byte cap.
- **AG-51** [A] — A run MUST stop at the step limit of AG-25 and MUST hand the last failing log to the user rather than retrying indefinitely.
- **AG-52** [A][S] — Cancelling a run MUST stop the workspace, invalidate its ticket, and leave the commits already pushed untouched.

## 15. The Portal as the Builder of Static Applications

- **AG-53** [A][S] — When the Portal makes a model call for a run itself, it MUST call `jc-agent-proxy` with the run's own ticket exactly as a workspace would, so the model key stays in the proxy and the run's token budget and audit log cover the call (AG-35, AG-41, AG-42).
- **AG-54** [A][S] — A model's answer MUST be treated as untrusted text: only the SEARCH/REPLACE blocks addressed to the run's editable files (`spec.json`, `index.html`) are applied, the specification they produce MUST be validated against the kit's schema before it reaches a browser, and a page they produce MUST reach a browser only inside the sandboxed preview frame or behind the application's login, under a policy that names the script hosts it may load from and allows no call with a session (AG-20, AP-50, AP-58).

## 16. What the Assistant Did, and Where It Looks When Something Fails

- **AG-56** [A][H][S] — A `tool` run event MUST carry the tool's name, its input, its output or its error, a status (`ok` or `failed`) and its duration, so every step the assistant took is inspectable in the conversation (OPS-50, API/04 §4). The payload is untrusted text (AG-46): the Portal MUST render it as text and never as markup, and the proxy MUST redact a bearer token, a cookie, a password, an API key or a connection string that slips into it before the event is stored (AG-40).
- **AG-57** [A][S] — The agent proxy MUST offer the assistant one diagnostics door, `GET /v1/diagnostics/{component}/{id}`, forwarded with the run's own ticket to the Portal, which answers only for a resource of the run's project: `pipeline` (the runner's counters) and `change` (the change's state, lane and merge or apply error); an unknown component or an id that is not a name is refused with `400` before anything is fetched. The body MUST pass the same redaction as AG-56 and the call MUST be audit-logged like every proxied request (AG-42).

## 17. The Assistant Finds Data

- **AG-58** [A][H][S] — The Portal MUST answer `GET /api/v1/projects/{project}/assistant/catalog?q=…` for a signed-in caller with the Context Spaces, Endpoints and DataModels of the project whose name, title, description, labels, slug or classes match the words of `q`, each item carrying its `kind`, `name`, `space`, `owner` (the project), `matchReason`, an `access` verdict with its reason (`allowed` when the endpoint's audience admits the caller: `public`, `organization` for a signed-in member, `projectList` naming the project; `restricted` otherwise, disclosing nothing beyond the name and kind, EP-55 stays the last word for data) and `freshness` (the counters and time of the pipeline that feeds the endpoint, read from the runner, `null` when nothing feeds it or the runner does not answer). The same search MUST be the assistant's `search_catalog` tool (Architecture/07 §2): a run that answers a person's question MUST run it over the mirror and publish the result as a `tool` event named `search_catalog` (AG-56), so the answer is grounded in the manifests and never in a guessed URL (AG-12, API/01 §18).

## 18. One Operation Registry Behind Every Door

- **AG-59** [A][H][P][S] — Every action the Portal offers a person MUST be an operation of one registry: a `jc_`-prefixed name, a JSON Schema draft-07 input and output, MCP annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`), the roles it needs (PF-50) and the lane it takes (CC-70). The REST route, the assistant's tool, the agent proxy's tool and the MCP tool of an operation MUST be adapters over the same function; a route the registry does not know is a defect (CC-48, ADR-N-021).
- **AG-60** [A][S] — The Portal MUST serve an MCP server at `/api/v1/mcp` (Streamable HTTP, stateless, protocol `2026-07-28` with `server/discover`): `tools/list` is the registry filtered by the caller's effective permissions, `resources/read` serves manifests, kinds' schemas, a model's artifacts, a draft and a change's plan the caller may read, `prompts/list` carries the guided units, results are structured (CC-47), and a call longer than a request answers through the Tasks extension. It MUST accept a bearer whose `aud` names the Portal and nothing else (no edge session), MUST publish RFC 9728 protected-resource metadata and answer an unauthenticated call with `401` and `WWW-Authenticate` (as AG-32), and MUST apply per-token rate and byte limits.
- **AG-61** [A][H][S] — A draft (project, kind, name) MUST be kept by the Portal, not by a browser tab: the manifest being worked on, its last verdict (AG-62), who last touched it (person, run, MCP client or API key) and a version. Every operation that edits, checks or proposes MUST read and write the draft, every open Portal window and instance MUST show a draft's change within the activity stream's latency (UI-47), and an assistant's `navigate` MUST open a draft, not carry the form's values (UI-45).
- **AG-62** [A][H][S] — Every check operation (manifest dry run, pipeline test PL-43, LinkML validation DM-55, schema validation, endpoint access) MUST answer one `Verdict`: `ok`, `findings[{level, path, message}]`, an optional `trace`, `checkedAt` and the digest of the input it judged. A propose operation MUST refuse a draft whose verdict is absent, red or older than the draft's version, with an error that names the check to run; in a strict installation (PF-57) the refusal has no override.
- **AG-63** [A][H][S] — An MCP call that would take a Yellow or Red lane, or carries `destructiveHint`, MUST NOT proceed on the agent's word: the server MUST ask through elicitation (form mode for a value, URL mode opening the draft in the Portal for a confirmation) and MUST record the person's answer on the run's timeline (AG-56).
- **AG-64** [A][S] — The in-process assistant and the agent runner MUST call operations only through the registry: the assistant as a model loop over the registry's tools, the runner through the Portal MCP behind the proxy with the tools presented as a code API loaded on demand; neither MUST hold a second implementation of an operation, and the workspace holds no credential (AG-34, AG-35).

## 19. Builder Egress Allow-List and Lease Expiry

- **AG-65** [A][S] — The agent proxy MUST expose `GET /v1/fetch?url=` for builder internet egress using HTTPS only; the target host MUST match the `AgentProfile` `egress.allow` exact-host allow-list, redirects MUST target allow-listed hosts only, and responses MUST be capped by size and restricted to text, JSON, or markdown content types; the proxy MUST enforce `egress.maxBytesPerRun` advertising remaining budget in a response header and returning HTTP 429 problem details when spent, MUST strip inbound `Authorization`, cookies, and tickets, MUST refuse URLs containing userinfo, and MUST log one audit record per fetch (run id, host, status, bytes, duration); an `AgentProfile` without an `egress` block MUST permit no egress, and data read via fetch MUST NOT become a runtime dependency of the published application (AP-49, AP-65).
- **AG-66** [A][S] — The Portal background reconciler loop MUST automatically transition an agent run whose lease time has elapsed to `expired`, terminate its workspace Job, invalidate its ticket hash, and record the expiration reason on the draft application record (AG-52, AP-68, AP-70), executing strictly on schedule without relying on user page loads.

## 20. Conversations, Unattended Work and Agent Access

- **AG-67** [A][S] — A conversation run created via `POST /api/v1/projects/{project}/assistant/conversations` MUST be assigned `kind: "conversation"`, require caller `propose` permission on `App` within the target project, initialize with no application name, endpoint slug, forge branch, or preview document, and answer turns in prose or by invoking registry operations without executing application dashboard passes within the conversation run (AG-59, AG-64).
- **AG-68** [A][S] — Continuing an ended conversation MUST be initiated as a new conversation run specifying `continues: <runId>` referencing an accessible prior run, rejecting direct messages to terminated runs with HTTP 409 Conflict, and the Portal MUST provide the prior transcript of user messages, assistant replies, and tool results to the model within profile token limits while rendering both runs as one linked thread (AG-41, AG-66, AG-67).
- **AG-69** [A][S] — An unattended work run (`application`, `dashboard`, or `analysis`) MUST NOT enter the `interviewing` state, recording autonomous decisions as `thought` events when ambiguity arises, and MUST terminate in `awaitingApproval` under governing profile lease and budget limits, proposing an `App` change for `application`, proposing a `Dashboard` manifest change for `dashboard`, or retaining a non-published `report.md` summary exportable via the kit for `analysis` (AP-20, AP-66, AG-41, AG-66).
- **AG-70** [A][S] — An `AgentProfile` manifest MAY define an optional `spec.access` block specifying permitted operation names, kind verbs, and endpoint verbs, which the platform MUST intersect with the initiating user's effective permissions at the time of each call, defaulting profiles without an `access` block to read-only operations carrying `readOnlyHint: true`, presenting only this effective tool set to the model, and rejecting out-of-scope calls as refused `tool` events before execution (AG-03, AG-56, AG-59, MF-40).
- **AG-71** [A][S] — The agent runs endpoint `GET /api/v1/projects/{project}/agent-runs` MUST support filtering by `kind`, `status`, `mine`, and `app`, restricting returned runs to the caller's own executions unless the caller holds the `portal-approver` role in the project, and every `AgentRun` resource MUST include `kind`, `unattended`, and `continues` attributes (AG-43, PF-50).
- **AG-72** [A][P] — `AgentProfile.spec.model` MAY carry `reasoningEffort` (`low`, `medium` or `high`), and the Portal and the agent proxy MUST send it as the provider's reasoning setting on every model call of a run of that profile; absent, no reasoning setting is sent.
- **AG-73** [A][H] — A conversation run given an external feed's URL, optionally with a description and a specification of its data, MUST integrate it with one `jc_space_complete` call carrying the URL, the context space, the entity type named by the description or specification (`typeName`) and the description (`description`), MUST open the Complete this space page on the resulting drafts, and MUST NOT propose the change itself; `jc_space_complete` MUST name the inferred class `typeName` when given and carry `description` onto the drafted model, space and data source (AG-59, AG-61, AG-62, DM-54, PL-39).
- **AG-74** [A][H] — A conversation run asked to keep an indicator up to date MUST answer with one `draft_kpi_pipeline` call (`name`, `type`, `attribute`, `agg`, optional `title`, `unit`, `q`, `sourceEndpoint`, `targetSpace`, and either `every`, a period of at least one minute, or `onChange: true` with optional `watchedAttributes`), from which the Portal MUST draft a `Pipeline` reading the source Endpoint and writing one `KeyPerformanceIndicator` per run into the target indicator space (`{project}-kpi` when none is named, a name not ending with `-kpi` given that suffix), MUST draft that space's `ContextSpace`, `Endpoint` and write and read `Policy` manifests when the space does not exist, MUST test the pipeline (PL-43) on a page read through the run's endpoint when the source is that endpoint and on an empty page otherwise, keeping the verdict on the draft, MUST open the pipeline form on the draft and MUST NOT propose anything itself; the indicator card MUST offer to keep its indicator updated through the same call (PF-54, PL-45, PL-51, AG-61, AG-62).
- **AG-75** [A][H] — A conversation MAY be started with up to five endpoints the person picks in the assistant (`endpointNames`), and the person MUST be able to change them with any later message of the conversation, from a data bar above the text box and from a Use action on an endpoint the catalog search shows; for those endpoints the conversation run MUST offer the data-plane MCP tools of each endpoint (`describe_access`, `describe_schema`, `query_entities`, `get_entity`), call them through `jc-agent-proxy` with the run's ticket at `/v1/data/endpoints/{slug}/mcp` so the gateway applies the person's grants, record every call as a `tool` event named `query_endpoint` with the endpoint, the MCP tool, its arguments and its result, feed the result back to the model for at most six calls per message, and answer the person from the results with the entities it used; it MUST NOT call a write tool of the façade (AG-49, AG-58, AG-70, SP-19).
- **AG-76** [A][H] — A conversation run MUST work with the data as an agent, not in one fixed call: (1) besides the endpoints the person chose (AG-75), the model MAY call the MCP tools of any Endpoint of the project the catalog search reports `allowed` for the person and the profile grants (AG-58, AG-70); the Portal MUST add such an endpoint to the conversation before the call, as if the person had used it from the data bar (an `endpoints` event, at most five), and `jc-agent-proxy` MUST re-read the run from the Portal once when a call names a slug its cached run does not, instead of refusing it; (2) one model answer MAY carry several `query_endpoint` blocks, across one or several endpoints, which the Portal MUST run concurrently and return together, each as its own `tool` event, counted against at most twelve calls per message; (3) `compute_kpi` and `draft_kpi_pipeline` MUST name the endpoint they read (`endpoint`, `sourceEndpoint`) when the conversation has none, and the Portal MUST read that endpoint's entities through its own proxy route; (4) a `draft_kpi_pipeline` whose plan is refused or whose Bento test on a page of the source is not green MUST go back to the model with the refusal or the verdict, so it inspects the data again and drafts a corrected pipeline, at most three drafts per message, and only a green draft opens the Pipeline form; a `compute_kpi` whose read fails goes back the same way. No write tool of the façade is ever offered (AG-49).
- **AG-77** [A][S][H] — Every kind the resource API serves (MF-11) MUST be listable, readable, proposable (create and update) and proposable for deletion through four channels that reach one registered operation per action (ADR-N-021): the Portal's lists and forms, the REST routes `/api/v1/projects/{project}/{plural}`, the operations registry (`jc_resource_list`, `jc_resource_get`, `jc_resource_propose`, `jc_resource_delete`, `jc_change_reject`, and so every MCP client of `/api/v1/mcp`) and the assistant (`change_resource`). One input MUST give the same Verdict and the same Change plan whichever channel sent it (PF-57). A proposal MUST be refused without a fresh green verdict, naming the check to run; a literal secret MUST be refused before a branch exists (MF-24); a deletion MUST take the Red lane with the name typed back (CC-19, CC-39) and MUST be refused with `409` naming the resources that still reference the target. The caller MUST hold the kind's verb in a RoleBinding and, for an agent, in its AgentProfile (AG-70), or the answer MUST name the missing verb; a RoleBinding, Role or ServiceAccount MUST NOT grant more than its proposer holds on that scope. The assistant MUST open the kind's form, or the deletion's confirmation, prefilled and MUST NOT propose on its own (AG-73); an operation called by an agent MUST NOT approve (AG-11), and a person approves, an administrator also their own change (PF-58). Writing entities stays with the endpoint's own tools (AG-49).
- **AG-78** [A][S][H] — A conversation MAY prepare a change to entities the person asks for, as a `write_entities` call naming one endpoint and at most 50 entities by id, each with the attributes that change and their new values; the Portal MUST read the person's grants on that endpoint (`describe_access`) and each entity (`get_entity`) through `jc-agent-proxy` with the run's ticket, MUST refuse an entity whose type or attribute the grants do not let the person update (`updateAttrs`), or that the person cannot read, with the reason back to the model, and MUST publish the preview as a `tool` event named `write_entities` carrying every attribute's value before and after. The write MUST run only when the person presses Apply on that preview, from the browser with the person's own session, as one `PATCH /api/endpoint/{slug}/ngsi-ld/v1/entities/{id}/attrs` per entity, so the gateway's policy decides each one (EP-55); neither the Portal nor the run writes an entity or calls a write tool of the façade, Cancel sends nothing, and a refused write shows the gateway's reason (AG-20, AG-73, AG-75).
- **AG-79** [A][H] — `jc_space_complete` given a URL MUST shape the drafts after the feed's records, not its envelope: (1) it MUST find the records in the probe's sample (the sample when it is an array of objects, a GeoJSON FeatureCollection's `features`, otherwise the largest array of objects at most three levels deep) and infer the model from those records; (2) the drafted Pipeline's mapping MUST write one entity per record with the id `urn:ngsi-ld:{Type}:{orgDomain}:{space}:{localId}`, `localId` taken from the record's field whose values are unique in the sample, `location` as a GeoProperty from a latitude/longitude pair or a feature's geometry, and every other scalar field as a Property under the slot name the inferred model gives it, a null value left out; (3) when the records carry a position it MUST also draft a `Layer` over the drafted Endpoint, drawn as circles coloured by the first numeric attribute that is not an identifier, a time or a coordinate, and a `Dashboard` named after the space with one full-map page drawing it, with `project` visibility, checked with the other drafts and proposed in the same change; (4) every verdict it stores MUST be taken on the manifest the draft holds, so a completion whose checks are green is ready to propose (AG-73, DM-54, PL-39, UI-19).
- **AG-80** [A][H] — A conversation run MAY ask the person while it works: `jc_ask` publishes a `question` event carrying a JSON Schema, a default answer and its options (or a kind to pick from, AG-83), and the loop waits for the `answer` before it calls again, taking the default when the person closes the question or the run reaches its wall clock. An unattended run MUST NOT call it (AG-69): it records the assumption as a thought instead. The question's text and its options are the model's words rendered as text, never as markup or a link (AG-20, AG-44).
- **AG-81** [A][S] — The Portal's MCP resources are addressed `jc://{project}/{plural}/{name}`, with `jc://schemas/{Kind}` for a kind's schema, `jc://{project}/drafts/{Kind}/{name}` for a draft, `jc://{project}/changes/{changeId}` for a change's plan and `jc://{project}/datamodels/{name}/linkml` for a model's source. A resource of the organization itself — `Role`, `RoleBinding`, `Group`, `Organization`, `Project`, `AgentProfile`, `ServiceAccount` — belongs to no project and is addressed `jc://-/{plural}/{name}`: `-` is not a DNS-1123 label, so it can never be the name of a project. Reading one MUST ask the same permission the REST route asks (PF-59), so a caller who may not read `RoleBinding` is answered as if it were not there, and `resources/list` MUST list the organization's resources the caller may read beside the project's.
- **AG-83** [A][S] — A question MAY name a kind instead of listing options (`pick`: `endpoints`, `spaces`, `datamodels`, `pipelines`, `datasources`, `policies` or `projects`); the platform MUST fill the options from what the asking person may read in the project, through the same check the REST listing of that kind makes, each with its name as the value, its display title and one line of description (an endpoint: its space, representations and audience; a space: its broker). The model MAY narrow the list by name and MUST NOT be able to add a resource the person cannot read. The platform MUST refuse an answer that is not one of the options it offered, and MUST NOT cut the options it offers to a fixed count.

## 21. Agents in Workspaces

- **AG-82** [A][S] — An agent MUST work in a workspace when it changes more than one resource (CC-76), MUST present the comparison before it offers to bring the work back, and MUST NOT bring it back or approve it itself; its workspace carries a TTL ([ADR-N-024](../Decisions/adr-n-024-workspaces-branch-and-preview.md)).
