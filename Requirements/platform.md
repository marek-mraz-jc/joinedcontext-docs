# Platform & Domain Invariants

Family **PF** (PF-01…PF-106). Owning chapters: [Architecture/03-domain-model.md](../Architecture/03-domain-model.md), [Architecture/12-identity-and-access.md](../Architecture/12-identity-and-access.md), and [Architecture/17-artifact-store.md](../Architecture/17-artifact-store.md). Verified by: [Testing/04-configuration-and-pipeline-tests.md](../Testing/04-configuration-and-pipeline-tests.md).

## 1. Instance and Organization Invariants

- **PF-01** — An Instance SHALL represent exactly one physical deployment of the platform operating under a shared ingress domain and single Keycloak realm, and SHALL host exactly one Organization; a second organization is a second Instance, with its own domain, realm, configuration repository and gateway org domain.
- **PF-02** — An Organization SHALL be the highest-level administrative unit within an Instance, mapped to exactly one Git repository in the internal forge and one Keycloak subtree. The repository part is superseded by PF-85: an organization repository plus one repository per Project.
- **PF-03** — An Organization MUST have at least one assigned Organization Administrator identity.
  > Note: The platform prevents the deletion of the final remaining administrator identity within an Organization.
- **PF-04** — User accounts, user groups, and custom roles SHALL be owned strictly by an Organization.

## 2. Projects and Context Spaces

- **PF-05** — A Project SHALL represent a collaborative domain owned by exactly one Organization, serving as the boundary for resource grouping and pipeline runner isolation.
- **PF-06** — A Context Space SHALL correspond to exactly one logical NGSI-LD tenant within the context broker data plane.
- **PF-07** — Every Context Space MUST be owned by exactly one Project, mediating cross-project data access strictly via Endpoints (EP-01) or Context Source Registrations.
- **PF-08** — A Context Space SHALL contain zero or more Data Models, Security Policies, Scope Definitions, Subscriptions, Context Source Registrations, and Seed Entities.
- **PF-09** — The Context Space identifier MUST be unique within an Instance and MUST consist only of lowercase alphanumeric characters and hyphens (`^[a-z0-9-]+$`), matching the `{space}` component of entity URNs.

## 3. Deterministic Identity and Naming

- **PF-10** — All entities, schemas, and configurations managed within a Context Space MUST adhere to the URN naming standard specified in ADR 001: `urn:ngsi-ld:{Type}:{orgDomain}:{space}:{localId}`.
- **PF-11** — Resource manifests stored within the repository MUST use deterministic identifiers derived mechanically from the file path and organization namespace per CC-10.
- **PF-12** — Random UUIDs MUST NOT be used for entity identities, space names, or pipeline identifiers, preserving prefix-matching properties for Context Source Registration routing (R33, R34).

## 4. Deletion, Lifecycle, and Cascading Constraints

- **PF-13** — Deletion of any managed platform resource MUST follow the explicit deletion protocol specified in CC-19 and CC-39 without automated unflagged deletions.
- **PF-14** — A Project MUST NOT be deleted if it contains active Context Spaces or running resident Pipelines.
  > Note: All contained Context Spaces and Pipelines must be decommissioned and reconciled prior to Project removal.
- **PF-15** — Deletion of a Context Space MUST cascade to all contained Endpoints, Subscriptions, and Context Source Registrations during the same reconciliation wave.
- **PF-16** — Seed entities managed via Git manifests MUST NOT be deleted by the reconciler if live telemetry has appended child properties, unless force-deletion is explicitly approved via the Red approval lane (CC-63).

## 5. Quotas and Resource Accounting

- **PF-17** — Platform settings MUST enforce structural quotas per Organization and per Project for active Context Spaces, resident streams, public Endpoints, and ingestion throughput.
- **PF-18** — Quota limits MUST be evaluated deterministically during CI manifest validation via Conftest policy checks (CC-60).
- **PF-19** — Ephemeral sandboxes (CC-67) MUST be governed by distinct, bounded quota limits and an enforced Time-To-Live not exceeding 14 calendar days.

## 6. Export, Import, and Project Duplication

- **PF-20** — The configuration state of any Project or Organization at any Git commit revision MUST be fully exportable as a standalone archive per CC-49: a project as the bundle the Portal and `jcctl` build from `projects/{project}/` (PF-22), an organization as the configuration repository itself at that revision, which a mirror clone carries whole (OPS-11).
- **PF-21** — The exported archive MUST include all directory manifests, pipeline configurations, data models, blueprint instances, dashboards, and UI configurations without plaintext secret values.
  > Note: Secret references (`secretRef`) are preserved while raw credentials are excluded.
- **PF-22** — Project duplication MUST be supported as a single declarative action copying the project directory, updating the target namespace and `{orgDomain}` bindings, and applying via `jcctl` per CC-50.
- **PF-23** — Replaying an exported Project into a fresh, empty platform deployment MUST fully reconstruct all spaces, endpoints, data models, pipelines, and gateway routes without manual intervention.

## 7. Multi-Language Metadata

- **PF-24** — Human-facing metadata a person authors MUST be a single plain-text string in the author's language, as UI-50 requires; the legacy `{locale: text}` map keyed by ISO 639-1 codes still parses and resolves per PF-28.
  > Note: This reverses what PF-24 used to say. `ObjectMeta.title` and `ObjectMeta.description` are `Text`, which is `Plain(String)` or the legacy `Localized` map (`crates/jc-core/src/i18n.rs:148`), and the plain form is what every new manifest writes. PF-25 to PF-28 still govern the locales an Organization declares, the fallback, and how the legacy form and the Portal's own chrome resolve.
- **PF-25** — An Organization manifest MUST define an ordered list of supported locales, designating exactly one primary fallback locale.
- **PF-26** — Manifest validation in CI MUST verify that every human-facing metadata field provides at minimum a value for the Organization's designated fallback locale.
  > Note: This applies to a field still written as a legacy map (PF-24). A plain string is in the author's language and has no fallback locale to be missing.
- **PF-27** — Machine-translated metadata generated during automated workflows MUST be explicitly annotated with `machineTranslated: true` within the translation entry.
  > Note: The annotation is not built. No crate writes or reads `machineTranslated`, and no automated workflow translates metadata today.
- **PF-28** — Runtime metadata served over APIs or rendered within the Portal UI MUST resolve to the client's preferred locale based on content negotiation, falling back to the organization default.

## 8. Artifact Store

- **PF-29** — The platform MUST include one S3-compatible artifact store used for rendered, derivative, immutable objects including schemas, compiled mappings, dataset dumps, export bundles, and app build outputs.
  > Note: Git remains the source of truth for authored state and the database for runtime state; the store holds rebuildable derivatives.
- **PF-30** — The default artifact store component MUST be RustFS deployed in-cluster, relying solely on standard S3 primitives for object storage, multipart uploads, versioning, and object locking.
- **PF-31** — Object keys MUST be deterministic and namespaced by owner prefix (`schemas/{org}/{project}/{space}/…`, `endpoints/{slug}/…`), enforcing storage quotas and deletion cascades per organization.
- **PF-32** — Write access to the artifact store MUST be restricted to `jcctl` and CI jobs using scoped credentials, while the Context Gateway and Portal API hold read-only credentials without exposing pre-signed URLs.
- **PF-33** — Published artifacts MUST be written with compliance-mode object locking, while cached file downloads follow automated lifecycle purge rules.

## 9. Service Identities and Credentials

- **PF-34** — Every non-human writer or reader MUST act as a `kind: ServiceAccount` in a Project namespace with an accountable owner, purpose, scoped roles, and declared credentials.
- **PF-35** — ServiceAccounts MUST be principals of the same authorization model as users, compiling to standard `Policy` entities and evaluated through the in-process PDP (ADR-N-003). A ServiceAccount's grants MUST come from its manifest alone: a `groups` claim in a workload's token MUST NOT reach a `Policy` granted to a group, because Keycloak group membership of a service-account user is not a reviewed change (T-2545).
- **PF-36** — Credential secrets MUST NOT exist in Git or in manifests, storing only Argon2id key hashes, key identifiers, expiration timestamps, and IP allowlists in the database.
- **PF-37** — API keys MUST be accepted only as `Authorization: Bearer jc_{keyId}_{secret}` over TLS, while OAuth client credentials issue tokens with a lifetime not exceeding 15 minutes.
- **PF-38** — Credential rotation MUST support an overlap window during which both keys remain valid, propagating revocations to the gateway within 5 seconds across all replicas.
- **PF-39** — Direct writers MUST reach context data exclusively through the Context Gateway, with broker and database listeners blocked from external network reachability.
  > Note: The broker MQTT bridge authenticates devices with ServiceAccount credentials and enforces the same Policy set as HTTP writes.
- **PF-40** [H] — The Portal MUST provide a dedicated management interface listing every ServiceAccount, active credentials, request counts, and rotation actions.
- **PF-104** [S][A] — No answer a model reads MUST carry a credential. Minting or rotating an API key over the Portal MCP (`jc_service_account_key_mint`, `jc_service_account_key_rotate`) MUST answer a one-time claim instead of the token: a link into the Portal, bound to the person who asked, expiring after 15 minutes and spent by its first use. The key MUST be minted only when that person opens the claim in the Portal and confirms it, so the token reaches the person's screen and nowhere else (owner decision 2026-09-24, T-2359).

## 10. Entity identifiers and organization domain

- **PF-41** [S] — Every Organization MUST declare `spec.domain`, its verified internet domain; the reconciler MUST verify ownership (DNS TXT `_joinedcontext.{domain}` with the instance challenge, or the served `did:web:{domain}` document naming the instance host) before any Context Space of that Organization accepts writes, and MUST re-verify every 30 days.
  > Note: Half built. The Portal's reconciler mints each Organization's challenge, checks the TXT record and the `did:web` document, re-checks every 30 days and reports `status.domainVerification` on the Organization (`joinedcontext-portal/src/domain_verification.rs`). Nothing refuses a write yet: the `enforce` gate of [Architecture/03 §3](../Architecture/03-domain-model.md#3-identity-and-urn-specification) is not built, so a Context Space accepts writes whatever its Organization's state, and what stands between a declared domain and a false one is still the red-lane approval of the Organization manifest (T-2377).
- **PF-42** [S] — Entity identifiers MUST follow `urn:ngsi-ld:{Type}:{orgDomain}:{space}:{localId}` (Architecture/03): `{Type}` equals the entity's declared type, `{orgDomain}` equals the owning Organization's `spec.domain`, `{space}` equals the target Context Space name, `{localId}` matches `^[A-Za-z0-9._~-]{1,128}$`.
- **PF-43** [S] — The Context Gateway MUST reject with 400 (RFC 7807) any create, upsert or batch write whose entity id violates PF-42 for the resolved tenant, including ids that name another Organization's domain or another space; `jcctl` and CI MUST apply the same validation to seed entities, Policy and ScopeDefinition ids and to `idPattern` values of subscriptions and registrations.
- **PF-44** — Blueprints, the LinkML Editor's example generator and a Bento mapping over the reconciler-injected `JC_ORG_DOMAIN` MUST be the only id-minting paths in generated code, and a pipeline file MUST NOT write an organization domain as a literal; the Context Space name MUST be unique within its Organization (PF-09 is satisfied per Organization, and `{orgDomain}` makes the pair globally unique).

## 11. One identity provider for users, apps and workloads

- **PF-45** [S] — Keycloak MUST be the only identity provider: humans authenticate through OIDC (the Portal and every app behind the APISIX `openid-connect` login front on `portal.{domain}` and on every App's host `{name}.apps.{domain}`, ADR-N-019, ADR-N-037; CLIs through the device flow); every non-human caller, including platform components, pipelines, apps, addons, conformance runners and any third-party service deployed in the clusters, MUST be a `ServiceAccount` with an `oauth-client` credential and MUST call other services with a short-lived `client_credentials` JWT audience-bound to the callee (RFC 8707); static keys between cluster services MUST NOT exist (API keys are for external systems only, PF-36).
- **PF-46** [S] — Every bearer token MUST be verified by the service that acts on it: the Portal and the Context Gateway MUST check issuer, signature, `exp`, `nbf` and audience against the realm JWKS, and the Context Gateway MUST map `azp` to the `ServiceAccount`, before the request reads or changes anything; the verifier MUST support the realm's signature algorithm (ES256, AR-11), and a route whose upstream does not verify MUST stay closed rather than open. The edge proxy MUST NOT be relied on as the verifier; it routes, rate-limits and strips forgeable inbound headers (ADR-N-019). A service exposed by an organization inside the cluster MAY be registered as a Keycloak client and MUST then accept the same tokens, so services communicate with each other through Keycloak-issued identities only.
- **PF-47** [S] — A `ServiceAccount` MAY bind a cluster workload through `spec.workload.kubernetes: { namespace, serviceAccount }`, and the workload then authenticates with no stored secret: the Portal's reconciler MUST provision the account's Keycloak client (`{project}-{name}`) with federated client authentication (`clientAuthenticatorType: federated-jwt`) trusting the realm's identity provider `kubernetes` for the one subject `system:serviceaccount:{namespace}:{serviceAccount}`, with `client_credentials` as its only grant and audience mappers for the slug of every Endpoint of the project on a space one of the account's roles scopes, plus `portal-api` when one of its roles names a `Role` (§2a of Architecture/12). The workload presents its projected Kubernetes ServiceAccount token, audienced to the realm issuer, as `client_assertion`; no client secret is mounted, shown or stored anywhere. The reconciler is the only writer of such a client: it marks it `managed-by: joinedcontext`, writes drift back, deletes it when the manifest is removed or loses `workload`, and leaves a client of that id it did not create untouched and reported. The realm MUST declare the identity provider `kubernetes` with the cluster's service-account issuer (owner decision 2026-09-25, T-1513; no RFC 8693 token exchange).

## Federation identity

- **PF-48** [S] — A hub space's broker tenant reads member tenants directly through the registration's `tenant` member (CIM 009 clause 4.3.6.5); the hub Endpoint's policy set is the only gate on a federated read, so registering a member is the act that exposes it to the hub's audience (a Red-lane change signed by a steward, CC-63); a `ContextSourceRegistration` whose member space is outside the hub's project MUST be refused at validation; `spec.federation.identity: caller` MUST answer `501 Not Implemented` (RFC 7807 problem document) until token exchange exists; partial answers (`207` with `NGSILD-Warning`) MUST pass through unchanged (EP-70), and system attributes (`createdAt`, `modifiedAt`) MUST survive read policy masking to preserve source provenance (EP-71).

## Roles as code

- **PF-49** [S] — Who may change configuration MUST be declared in the Organization repository, not in the identity provider: `kind: Role` (`spec.rules[]`: `kinds`, `verbs` from `propose`, `approve`, `delete`, optional `constraints` on a spec field or `metadata.name`, each with one of `in`, `notIn`, `equals` or a whole-value `pattern`) and `kind: RoleBinding` (`spec.subjects[]` of `user` or `group`, `spec.role`, `spec.scope` of exactly one `organization`, `project` or `contextSpace`, optional `spec.validity`), the same binding shape a `ServiceAccount` carries (PF-34), whose `roles` naming a `Role` are in force for a bearer token of the account's derived Keycloak client (`azp`), `approve` excepted (PF-58, [Architecture/12 §3](../Architecture/12-identity-and-access.md#3-service-identities)). Keycloak supplies identity and group membership only; a token carries no permission (I4, PF-45).
- **PF-50** [S] — The Portal MUST evaluate every `POST`, `PUT`, `PATCH`, `DELETE` and every approval against the bindings whose scope covers the target project before a `Change` exists, and MUST answer `403` (RFC 7807) otherwise; a principal with no binding reads and proposes nothing; `approve` is a verb scoped like the others and replaces any realm-wide approver role; `delete` is never implied by `propose` (CC-62).
- **PF-51** [H] — The reconciler MUST compile the bindings into the forge (`CODEOWNERS`, team permissions) and into a policy data file the organization repository's CI evaluates with Conftest, so a merge request written outside the Portal is bound by the same rules (CC-41, CC-42, CC-59) and only the Portal's own identity moves the default branch (PF-105); `GET /api/v1/projects/{project}/permissions/me` MUST return the caller's effective rules and the UI MUST hide what they deny, never being the point of enforcement.
- **PF-52** — A change to a `Role`, a `RoleBinding` or the lane policy is always red lane (CC-70); `policies/tests/` MUST hold executable cases for the role model (a viewer cannot propose, a developer cannot publish a public Endpoint, deletion needs `delete`) that CI runs; the one group that bootstraps organization administration is named in the platform settings file and is the only binding read from the identity provider.
- **PF-56** [S] — The platform ships one role taxonomy every organization starts from, as `kind: Role` manifests in `users/roles/` of the Organization repository (PF-49), and the Portal, the forge and CI enforce it the same way (PF-50, PF-51): `viewer` (`read` on every project kind, PF-59; bound at organization scope to every signed-in person when `Organization.spec.projects.visibility` is `organization`, to nobody when it is `members`, PF-61), `model-editor` (`propose` on `DataModel` and `Mapping`), `pipeline-editor` (`propose` on `Pipeline` and `DataSource`), `endpoint-editor` (`propose` on `Endpoint`), `app-editor` (`propose` on `App`), `steward` (`propose` and `approve` on every project kind, `approve` on `Endpoint` constrained to a non-public audience: the domain lead who approves the yellow lane), `publisher` (`read` on every project kind and `approve` on `Endpoint` constrained to `spec.audience` in `[public]`: who may let data out to the public, PF-71), and `org-admin` (`propose`, `approve` and `delete` on every kind, `Role` and `RoleBinding` included: the one role that approves the red lane, CC-70). An editor role never carries `approve` or `delete`, and no role of the taxonomy grants a verb outside its kinds; the taxonomy is a seed a person extends by proposing further roles, never a fixed list the Portal hardcodes (Architecture/12 §2a).

## Sharing across organizations

- **PF-53** [H][S] — What one project shares is visible to the projects it shares with: the Portal MUST list, for a project, every Endpoint of another project of the repository whose audience admits it (`organization`, or `project-list` naming it), and MUST let a person of that project declare the `SharedSpaceReference` in one action, as a Change (EP-15, CC-34); an Endpoint whose audience does not admit the project MUST NOT be listed there. The same list is what the assistant's catalog search reports as `restricted` or `allowed` for the caller (AG-58), so a person and an agent read one truth about who may reach what.

## Key performance indicators

- **PF-54** [S] — A project's indicators live in Context Spaces of their own whose names end with `-kpi` (unique in the Organization, PF-44): `{project}-kpi` by default, or a space per subject the author names, such as `transportation-kpi`; every indicator is one NGSI-LD entity of type `KeyPerformanceIndicator` with the id `urn:ngsi-ld:KeyPerformanceIndicator:{orgDomain}:{kpiSpace}:{indicatorName}` (PF-42) and the attributes of Architecture/03 §2: the Properties `name`, `calculationFormula`, `currentValue` (with `unitCode`, a UN/CEFACT code, and `observedAt`), `calculationPeriod` and `updatedAt`, and the Relationships `derivedFrom` and `computedBy`. The type and its terms follow OASC MIM8 (ecosystem indicators) and ISO 37120 where a named indicator exists; a broker, a Data MCP tool, a Dashboard and an Endpoint treat the space like any other, so an indicator written there is readable the moment it is written, through the space's Endpoints and their Policies.
- **PF-55** [S] — An indicator MUST carry its provenance or be refused: `derivedFrom` names the Endpoint URN the source entities were read through (and the source entity URNs when they are few), `computedBy` names the Pipeline URN or the agent run URN (`urn:ngsi-ld:AgentRun:{orgDomain}:{project}:{runId}`) that computed it, and `calculationFormula` says how (PL-36); `jc-core` and the gateway (PF-43) MUST reject an indicator without them. An indicator is written like every entity, through an Endpoint of the `{project}-kpi` space and its Policy (PF-39): a Pipeline writes with the runner's service account (PL-18), and an indicator the assistant computed is written by the person who asked, with their own session, after they saw the value; the assistant itself writes nothing (AG-20).
- **PF-57** [S] — An installation MUST declare `platform.validation` as `strict` or `lax` in its values; `strict` means no manifest is proposed, by any door and whether or not a draft names it, without a fresh green verdict for that exact manifest (AG-62) — a manifest proposed without a draft is judged by the check that ran on it (`?dryRun=All` on its route, or `jc_manifest_dry_run`, `jc_datasource_check`, `jc_pipeline_test`), which records its verdict under the manifest's own kind and name — and no Yellow or Red change is approved by its author, except the change of a person who administers every kind it touches, approved as it is proposed (PF-58, CC-34); `lax` lets a Green-lane draft propose with a warning. The value is shown in the Portal's header and answered by `GET /api/v1/branding`.
- **PF-58** [S][H] — A change a person proposes with their Portal session (the Portal's own or the edge's, never a bearer token) MUST be approved as it is proposed, in the same call and by the same path as the approve button, when a binding covering the project grants them both `approve` and `delete` on every kind of every file the change touches (the `org-admin` of PF-56, or a role a person extended that far): no second click and no pending entry in the approvals list. The merge commit is the record: `Approved in the Portal by {email}, its author, as an administrator of {kind}`; nobody else is named and nothing is anonymous. A red-lane change needs its typed name at propose (`?confirm=`, CC-19, CC-39): without it the change waits, and its author, still an administrator, approves it on its approval page with the name typed, the one self-approval the button keeps. The rule moves no other boundary: a change proposed by an agent run, a bearer caller or MCP is never approved this way, whoever started it (AG-11, AG-82), and a `ServiceAccount` never holds `approve`, whatever its roles say (PF-49); a person holding `approve` without `delete`, or both on some of the change's kinds only, proposes a change that waits for another approver (PF-70), and the propose dialog says so before the click, "Waits for an approver: you hold approve but not delete on {kind}"; membership of the bootstrap administrators' group is not a binding and does not count; any other author approving their own change is refused `403` `self-approval`. Auto-approval never grants a verb: it applies only where the proposer could approve the change and delete what it touches anyway, and a grant is still held to PF-52. The propose dialog says "Will be approved when you propose: you hold approve and delete on {kind}", and the result says "Approved as you proposed it, applying" instead of waiting for approval.
- **PF-59** [S] — `read` MUST join the verbs of a `Role` rule (`read`, `propose`, `approve`, `delete`); `propose` on a kind implies `read` on it, so a role written before this verb keeps working; every list, get, export, revision list, `permissions/me` and MCP resource MUST answer under `read` of a binding whose scope covers the target, and MUST answer `404` for a project the caller may not read, the one answer for "missing" and "not yours" (R20, PF-50).
- **PF-60** [S] — Scope inheritance MUST be additive: a binding at organization scope covers every project and every context space, a binding at project scope covers every context space of that project, a binding at context-space scope covers that space alone; a narrower binding never narrows a wider one, and no scope implies another project (PF-49).
- **PF-61** [H] — The platform MUST seed `viewer` as a `Role` with `read` on every project kind and MUST bind it at organization scope to every signed-in person of the organization when `Organization.spec.projects.visibility` is `organization` (the default), and to nobody when it is `members`; `org-admin` MUST read and list every Endpoint of the organization on the organization-level Endpoints page; `GET …/permissions/me` MUST show each inherited grant with the scope it comes from (PF-51, PF-56).
- **PF-62** [S] — Group membership MUST be declared in the Organization repository as `kind: Group` at `users/groups/{name}.yaml` (namespace `org`, `spec.members[]` of `user` e-mail, optional `spec.description`), reviewed in the red lane with `Role` and `RoleBinding` (PF-52); a member no Keycloak user carries yet is a warning at validation, and the binding takes effect on that person's first login (PF-04, PF-49).
- **PF-63** [S] — The reconciler MUST be the only writer of the Keycloak groups it manages (attribute `managed-by: joinedcontext`): it creates, renames and prunes members to match the manifests, overwrites a group edited in the Keycloak console on the next reconcile and reports the drift; a group without the attribute is never touched, and neither is a group a `RoleBinding` marks `source: provider` (PF-64): the identity provider owns its members, and the reconciler never creates, edits or prunes it. The bootstrap administrators' group of PF-52 stays the one grant read from the identity provider without a binding (PF-45, PF-51).
- **PF-64** [S] — A `RoleBinding` or `ServiceAccount` subject `group` MUST name a `Group` manifest of the organization, unless a `RoleBinding` subject marks it as a group of the identity provider with `source: provider` (a realm group such as the default group every signed-in person joins); validation MUST refuse a binding to an unmarked group with no manifest, so no binding silently matches nobody, MUST refuse the mark on a `user` subject and on any subject other than a `RoleBinding`'s, and MUST refuse a marked group that a `Group` manifest also declares, so no group has two owners (PF-49, PF-50, PF-63).
- **PF-65** [S] — Who may open a Project MUST be an Organization setting, `Organization.spec.projects.creation`: `anyone` (every signed-in person of the organization), `group: <name>` (the members of one `Group`, PF-62) or `org-admin` (the default when absent: `propose` on `Project` as for every kind, PF-50); the Portal MUST evaluate `POST /api/v1/projects` against that setting before a `Change` exists and MUST answer `403` otherwise (PF-05). Importing a project (MF-46) additionally needs an organization administrator (UI-87).
- **PF-66** [S] — The `Change` that creates `projects/{name}/project.yaml` MUST carry, in the same merge request, the `RoleBinding` `users/assignments/{name}-creator.yaml` that gives the creator `steward` at project scope, and nothing more than `steward`; the Change takes the yellow lane and is approved by whoever holds `approve` on `Project` (`org-admin`), or merges without a person when the setting is `anyone` and the installation is `lax` (PF-57); a later change to that binding is a red-lane change like every binding (PF-52).
- **PF-67** — A Project name MUST be unique in the Organization and MUST be a DNS-1123 label by the `{space}` rule of PF-09; the name is reserved by the open Change, so two people cannot open the same project, and a name once used is not reused while its history exists (PF-41).
- **PF-68** [S] — A `Role` MAY live in a Project, at `projects/{project}/roles/{name}.yaml` with `metadata.namespace` the project, besides the organization's `users/roles/`; a project role MUST name project kinds only (never `Role`, `RoleBinding`, `Group`, `Organization` or `Project`) and only verbs its proposer holds on those kinds at that project (PF-52); the same role name in `users/roles/` and in a project MUST be refused at validation (PF-49).
- **PF-69** [S] — A `RoleBinding` at project or context-space scope MAY reference an organization role or a role of that project; a project role MUST NOT be bound at organization scope or in another project, and a project role's `approve` or `delete` never reaches the `Role` or `RoleBinding` of another project (PF-50, PF-60).
- **PF-70** [S] — A project's steward, holding `approve` on `Role` and `RoleBinding` at project scope, MUST be able to approve that project's roles and project-scoped bindings in the red lane, held to PF-52 like every approver; `org-admin` keeps every right, and nothing lets a project steward grant a verb or a kind they do not hold (PF-52); a steward's own change still waits for another approver, since only `approve` and `delete` on every kind approve a change as it is proposed (PF-58).
- **PF-71** [S] — The taxonomy MUST seed `publisher`: `read` on every project kind, `approve` on `Endpoint` constrained to `spec.audience` in `[public]` and `approve` on `App` constrained to `spec.visibility` in `[public]`; the seeded `steward`'s `approve` on `Endpoint` MUST be constrained to `spec.audience` not in `[public]` and its `approve` on `App` to `spec.visibility` not in `[public]` (an App without one is `project`, AP-120), so publishing to the public is a right of its own that a domain lead does not hold by default; `org-admin` holds it by its unconstrained `approve` (PF-56, PF-49).
- **PF-72** [S] — Every door (the Portal, the REST API, the operations registry, the assistant, an import bundle) MUST require, for a `Change` that creates an Endpoint with `spec.audience: public`, moves one to it, creates an App with `spec.visibility: public` or moves one to it (AP-120), widens the Policy a public Endpoint uses, shares to a public Endpoint (`SharedSpaceReference`) or publishes a public hub (PF-48), an approval by a binding whose `approve` on the kind satisfies the public constraint, in the red lane with the typed confirmation (CC-19); a refusal MUST name the missing role, `publisher`, on every door alike (EP-76, PF-50).
- **PF-73** — `Organization.spec.projects.quota` MUST hold the default quota of every Project the organization opens (`contextSpaces`, `residentPipelines`, `publicEndpoints`, `ingestEventsPerSecond` of PF-17, and `apps`, `agentRunsPerDay`, `entitiesPerSpace`, `requestsPerMinute` per Endpoint); `Project.spec.quotas` MAY override a value below the default in the yellow lane, and an override above the default MUST take the red lane and an `org-admin` approval (PF-17, PF-52). `apps` MUST count the Apps whose `lifecycle` is `preview` or `published`, of every class: each one is built by the lane, routed and granted. A `draft` or a `retired` App MUST count nothing, because it runs, serves and is built nowhere (AP-18, AP-21, T-2654).
- **PF-74** [S] — The Portal's verdict (AG-62) MUST refuse, before a `Change` exists and on every door, the change that would exceed a quota of the project, naming the limit and the count (`pipelines 4 of 3`); the reconciler MUST NOT schedule a pipeline or an app beyond the quota, the agent runner MUST count runs per project per day against `agentRunsPerDay`, and an Endpoint that sets a rate limit MUST NOT set one above the project's `requestsPerMinute` (PF-18, EP-17). The quota is a ceiling on a limit that is set, only when the quota itself is set; it never gives an Endpoint without `spec.rateLimits` a limit (EP-20).
- **PF-75** [H] — The Project page MUST show each quota with its current usage, and `GET /api/v1/projects/{project}` MUST carry `status.usage` with the same numbers, so a person sees the limit before the verdict does (UI-44).
- **PF-76** [H] — A Context Space name is unique in the Organization (PF-44), so the Portal, the assistant and `jc_space_complete` MUST propose `{project}-{name}` by default and MAY accept a bare name when it is free; a collision MUST answer "taken by project {p}" when the caller may `read` that project and "taken" otherwise (PF-59).
- **PF-77** [S] — Deleting a Project MUST be one red-lane `Change` approved by `org-admin` or the project's own administrator (PF-70) that cascades explicitly and completely: every space (its broker tenant dropped after a data export was offered, CC-07), every Endpoint (slugs retired), every binding and project role, every app and its builds, every service account; a `SharedSpaceReference` from another project to one of its Endpoints MUST refuse the deletion until it is removed, naming it, so no grant and no reference outlives its project (PF-52, PF-69).
- **PF-78** — A deleted Project's name MUST stay reserved for a cooling period the organization sets, `Organization.spec.projects.nameCooldownDays` (default 30 days, `0` for none), counted from the commit that removed the project; `POST /api/v1/projects` MUST refuse the name until the period passes, saying when it becomes free. A Project moved to another instance MUST be deleted at the source only after the target has imported the bundle and reported every manifest's checksum from the bundle index equal (MF-42, PF-67).
- **PF-79** [H] — A person signed in with Keycloak MUST reach the organization's configuration repository in the forge with that same identity: the forge's OpenID Connect source MUST map a `groups` claim onto forge teams, and the platform MUST seed the team `readers`, holding every signed-in person of the realm, so nobody who may read the Portal meets a `404` in the forge; the organization and the repository stay private, so nothing is readable without a session (PF-49, PF-51, CC-41). Amended by PF-87: `readers` reads the organization repository only for a person holding a binding at the organization, and a project repository is read through that project's own teams.
- **PF-80** [S] — A forge team compiled from the organization's bindings MUST carry read access only, on the units a review needs (code, issues, pull requests); merging stays the Portal's approval and the repository's branch protection, so no team and no person pushes to the default branch, and the forge's `Owners` team stays the bootstrap administrator alone (CC-41, PF-51).
- **PF-81** [H] — Every forge link the Portal shows (a change's merge request, a manifest's file) MUST start the forge's Keycloak sign-in with the path as its return address (`/git/user/oauth2/keycloak?redirect_to=…`), so a person signed in to the Portal is returned to the file without a forge sign-in page, and a person without a session meets the Keycloak login, never a `404` (PF-79).

## Workspaces

- **PF-82** [S] — Every write into a workspace MUST pass the same permission, own-rights, secret and quota checks as a write into the main project (CC-76, PF-50, PF-51); a workspace grants nothing, and a preview counts against the project's quota.
- **PF-83** [S] — A preview MUST NOT be able to write into a Context Space of the main project, and MUST run paused unless a person starts a pipeline in it; real data reaches a preview only as an opt-in, bounded copy read through the origin's Endpoint with the person's own token (CC-78, [ADR-N-024](../Decisions/adr-n-024-workspaces-branch-and-preview.md)).

## Identity of a space

- **PF-84** [P] — The `{space}` segment of an entity id MUST be rendered as `{project}-{name}` from the Context Space's namespace and local name, unique in the Organization (PF-44, PF-76); `spec.urnSegment` MAY pin another value and MUST be used for every space that exists before this rule so that no entity id changes. A space copied to another project therefore gets a new segment by itself, and its data is loaded again under it.

## Project repositories

- **PF-85** — An Organization MUST map to one *organization repository* and one *project repository* per Project in the forge (supersedes the "exactly one Git repository" of PF-02 and CC-08). The organization repository MUST hold the organization-level kinds and the project registry (PF-86); a project repository MUST hold that project's kinds at its root (CC-85). An application keeps a repository of its own (AP-72).
- **PF-86** — The project registry MUST be the files `projects/{slug}.yaml` of the organization repository, `kind: Project`, each carrying `spec.repository` (a repository of the local forge by name, or an external git URL with a `secretRef`), `spec.ref` (the tag, branch or commit this deployment runs) and `spec.parameters` (this deployment's values, CC-88). The registry slug, not the repository name, MUST render `{project}` (CC-82), so two entries MAY point at one repository under two slugs.
- **PF-87** [S] — Membership of a project MUST be mirrored into the forge through the Keycloak groups `{slug}-readers` and `{slug}-writers` the reconciler keeps per project and the group→team mapping of PF-79: a binding in force at the organization or at the project granting `read` on the project's kinds MUST place the person in the forge team `{slug}-readers`, and `propose` or more in `{slug}-writers`; a binding scoped to one context space places nobody, since the repository holds every space. A team MUST carry access to its own project repository and to no other repository, so a forge token of a project member reaches that repository and nothing else; the organization repository MUST NOT be readable to a project member without a binding at the organization, and a person without a binding on the project MUST NOT be able to clone or read the project repository. An `org-admin` is an owner of the forge organization. Git MUST work over HTTPS with the person's own forge credential; the Portal MUST NOT proxy git.
- **PF-88** — Creating a project MUST create its repository from the template (`project.yaml`, `.jc/layout`, the CI workflow of CC-90, `CODEOWNERS`, a protected `main`) and its registry entry in one operation, both or neither. Deleting a project (the PF-77 cascade) MUST archive the repository, keep its name reserved for `nameCooldownDays` (PF-78) and remove the registry entry.
- **PF-89** [S] — Duplicating a project MUST be a fork in the forge, or an import of its bundle (MF-45), plus a registry entry under a new slug with parameters of its own; the copy MUST render its ids from the new slug and MUST NOT be able to write into the origin (PF-83).

## People and group roles

Decided in [ADR-N-031](../Decisions/adr-n-031-people-groups-and-app-groups.md) (T-2682).

- **PF-90** [S] — People MUST live in the organization's Keycloak realm and never in a manifest. The Portal MUST manage them through the Keycloak admin API and MUST write every action on a person to the activity log (actor, action, person, time) without any credential.
- **PF-91** [S] — The taxonomy MUST seed `people-admin` with `create`, `update`, `disable` and `delete` on the kind `Person` at organization scope, `org-admin` MUST hold it, and every people route MUST refuse anyone else with `403`, the Portal showing its controls disabled with the reason (UI-44).
- **PF-92** [S] — Creating a person MUST send Keycloak's execute-actions e-mail (`VERIFY_EMAIL`, `UPDATE_PASSWORD`). A realm without SMTP MUST instead get a temporary password with `UPDATE_PASSWORD` required, shown once to the creator and never stored, logged or returned again.
- **PF-93** [S] — The Portal MUST let a `people-admin` edit a person's name, change their e-mail (which then needs verifying again), disable them (ending every session), enable them, send a password reset, remove their second factor and sign them out everywhere. Deleting a person MUST propose one Change removing them from every `Group` and `RoleBinding` that names them, and MUST delete the Keycloak user only after that Change merges. A caller MUST NOT edit, reset, disable, sign out, remove the second factor of or delete a person who holds a right the caller does not hold (an `org-admin` above all), so the temporary password of PF-92 never opens a stronger account; nor disable or delete themselves or the last Organization Administrator (PF-03). The first is `403` naming the right, the second `409`.
- **PF-94** [H] — A person's page MUST list their groups, their platform roles with scope and their application roles, each linked to where it is granted.
- **PF-95** [S] — A group's page MUST edit its members, its `RoleBinding`s (a role at organization, project or space scope, PF-60, PF-69) and the `spec.access` entries naming it, each edit through the one propose function. Deleting a group MUST be one Change that also removes every binding and access entry naming it.

## Organization policies and limits

Decided in [ADR-N-035](../Decisions/adr-n-035-organization-policies-and-limits.md) (T-2714).

- **PF-96** [S] — Every organization-wide policy and limit MUST be a field of the `Organization` manifest: `spec.projects` (PF-65, PF-73, PF-78), `spec.policies` for the choices and `spec.limits` for the numbers, with exactly the entries, defaults, bounds and enforcers of ADR-N-035's catalog. An absent field MUST be its default, and an unknown field MUST be refused.
- **PF-97** [S] — The operator MUST set the bound of each entry in the deployment (`portal.organizationBounds`, read by the Portal from a mounted file), an entry left out keeping the catalog's built-in bound. The Portal MUST refuse, on every door before a `Change` exists and again at approval, an Organization change that crosses a bound, naming the entry, the value and the bound. No bound MAY be raised from the Portal.
- **PF-98** [S] — A `Change` to the `Organization` MUST take the red lane and need `approve` from an `org-admin` (PF-52).
- **PF-99** — Each enforcer MUST read the effective value of its entries (the project's override where the catalog allows one, then the organization's value, then the default) and apply a change on its next reconcile. The activity log MUST record each changed entry with its old and new value.
- **PF-100** [S] — Lowering a limit MUST refuse only new writes and new resources. It MUST NOT delete, stop or truncate what already exists; a project over a lowered limit MUST show it in its usage (PF-75).
- **PF-101** [H] — Every refusal by a limit or a policy MUST name the entry, its effective value and the usage where there is one, where the value comes from (the organization, the project or the default) and who may change it, for example "the organization allows 3 public endpoints (3 in use); an org admin can change this in Organization settings".
- **PF-102** [H] — Organization settings MUST show one section per catalog section. Each entry MUST show its value, its default, its bound and a one-line hint, and the page MUST show the effective values per project in one table.
- **PF-103** [S] — `spec.policies.apps.public: refused` MUST make every door refuse a Change that sets an App to `public` or moves one to it, citing the policy. Apps already `public` MUST stay public until a Change moves them (PF-100).
- **PF-105** [S] — The default branch of the organization repository MUST carry a branch protection rule the forge bootstrap converges on every apply: push and merge whitelists naming the Portal's own forge identity alone, `block_on_outdated_branch` and `dismiss_stale_approvals` on, and `required_approvals` 0, because the Portal's approval is the Verdict (CC-41) and what the forge adds is that nobody else moves the branch and nothing merges over an outdated base. The Portal MUST bring an outdated Change's branch up to date before it merges and merge only when the updated head still passes the Change's checks; otherwise the Change goes back to review with the reason. The bootstrap's seed MUST commit as the Portal's identity, never as the site administrator (PF-80, CC-41).
- **PF-106** [S] — Every forge token the platform mints MUST belong to a non-administrator machine user of its own, never to the site administrator: `jc-portal`, with `write` on the configuration's repositories and nothing else (a collaborator on the organization repository; in layout 2 also a member of a team of the configuration's organization that may create a project repository and writes the project repositories, CC-85, PF-89, MF-45); `jc-gateway`, with `read` on the same repositories and nothing else; and `jc-apps`, which creates and writes the generated applications' repositories in an organization of their own, `{org}-apps`, and holds nothing in the configuration's. A machine user MUST have no usable password and sit in no team that includes all repositories; a leaked token therefore reaches one repository with one verb, or the applications' organization, and never administers the forge (PF-51). A token is minted again when it no longer authenticates, and the workloads that hold it are restarted by the step that re-minted it.
